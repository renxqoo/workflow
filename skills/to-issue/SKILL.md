# to-issue（现象 → 结构化 issue：定位加工 → 查重 → 澄清 → 发布 → 回写）

本 skill 是三件套流水线的起点：**to-issue（问题定义）→ feature-dev（读 issue
实现）→ pr-review-loop（审查）**。核心信念：

**issue 是跨会话的唯一交接面——下游会话没有任何本次对话的上下文，
issue 里没写的事实对下游不存在；
issue 的价值上限不在模板，在定位加工——agent 能先复现、先定位，
把「现象」加工成「已定位的问题陈述」；
定位档位由证据决定不由感觉决定——宁可如实标档 1，不虚标档 2；
定位深度到「下游不必重新发现问题的存在」即停——不必到「下游可以直接
开写方案」，定位是给下游起点，不是替下游干活。**

## 阶段 0：入口判定（决定起点档位与初始上下文）

| 入口 | 识别 | 起点状态 |
| --- | --- | --- |
| **a 现象报告** | 用户描述「XX 不对/坏了/想要」 | 从零采证，档 0 起步 |
| **b 对话沉淀** | 本会话发现的范围外问题（「这个先记着」） | 对话上下文即初始证据，核实后可能直接档 1-2 |
| **c 审查残留** | pr-review-loop 落档不改的 finding / 轮次耗尽的「真实复杂型」残留 | 自带台账与证据——原样保留，档位按其证据级映射（见 locating.md）；
**过滤闸**：落档理由为「不认同是问题/惯例如此」的不建票（同入口 d
的闸），理由为「范围外值得单独处理」的才转 |
| **d 主动巡检** | agent 扫代码/日志/运行态发现异常 | 先过「值不值得建」闸：有具体后果才建，风格观察不建 |

入口搞错代价高：把 b 当 a 会重新采一遍已有的证，把 d 的风格观察建成
issue 会污染下游队列。

## 阶段 1：查重与合并（新建之前必做）

- 搜 open issue + **近期 closed**（已修复又复发是重要信号，closed 的
  issue 里可能已有定位历史）+ 关联 PR；
- 找到相近的 → **不新建**：把新证据（更好的复现、新的触发路径）评论
  补充到既有 issue，注明来源；定位档位高于既有 issue 时在评论里说明；
- 确认无覆盖 → 新建。查重结论（搜了什么、判定依据）写进 issue 草稿的
  元数据节——下游想知道这个问题是不是第二次出现。

## 阶段 2：类型判定 + 拆票判定

**类型三选一**（模板差异见 `references/issue-templates.md`）：

- **bug**：东西坏了。investigation（疑似未确认）不是第四类——就是 bug
  的档 0/档 1 状态，定位档如实标注即可；
- **feature**：新能力/改进。现象层换「用户痛点 + 现状基线」；
- **tech-debt**：结构清理。动机节强制——「为什么是现在」，没有时机的
  债务清理不如不建。

**拆票判定**（只对 feature/tech-debt 大需求）：预估 feature-dev 会判
「大级」（跨子系统/架构性）→ 拆为父 issue（问题定义 + 验收总纲）+
子 issue（垂直切片：每片可独立演示/验证，标 blocking 依赖）。切片
粒度自检：**子切片的 feature-dev 分级预期为中级**——预估某片仍会判
大级，说明切片不够垂直，再切。中小需求硬拆是仪式——不拆。
**bug 不拆票**：同根因多表现合并进一票，表现逐条列入现状节。

## 阶段 3：证据采集 + 定位加工（本 skill 的灵魂）

读 `references/locating.md` 执行完整纪律。要点：

- **三档定位**：档 2（复现定位，金标准）/ 档 1（静态定位，必须 ≥3 个
  排序假设 + 每条证伪条件）/ 档 0（纯现象，标「未定位」+ 列已尝试手段）；
- **档位由证据决定**：跑过复现命令且见过红才是档 2；
- **反过度定位闸**：目标是「下游不必重新发现问题的存在」。档 2 达成
  即停；一条回路尝试失败 + 假设排序完成即接受档 1；环境不可得
  （含需长时程运行观测的基线/流量时程）立即降档并写明缺什么；
- 档 2 的复现命令是全链路资产：issue 证据、feature-dev 的测试口径、
  pr-review-loop 的回归用例基础。

## 阶段 4：澄清（grilling 前沿轮询 + 裁决标注契约）

读 `references/clarifying.md`。要点：

- **代码可检索事实自己查**（永不问用户）；**环境事实要问但标
  `[环境事实，来源：用户]`**（生产日志/「XX」指哪个进程/基线数值
  ——代码里没答案但非决策，问一次即定）；**决策才问用户**
  （期望行为、优先级、不处理边界），每题带推荐答案，前沿轮询——
  一次问一批，前置已决才问后置；
- **裁决标注契约**（下游免重问的关键）：问过的决策在 issue 里标
  `[用户裁决]`；没问按默认处理的标 `[默认裁决，可否决]`。下游
  feature-dev 见前者不重问，见后者知道有否决窗口。

## 阶段 5：零上下文自检 + 发布

1. **零上下文测试**（按档位定及格线）：档 2 = 复现命令零上下文可重放；
   档 1 = 每条假设的证伪条件零上下文可独立执行；档 0 = 已尝试手段
   清单完整。依赖「对话记忆」的信息要么写进去，要么承认写不了。
   耐久性纪律：禁文件路径/行号（会腐烂），写接口/类型/行为契约；
2. **意图确认（非阻塞）**：一句话摘要（「本 issue 主张 X，不做 Y，
   定位档 N」）请求确认——发出后同一轮无响应即按 AFK 降级：推荐
   裁决自动生效 + issue 标「未确认发布」（元数据节），不阻塞；
3. 发布：类型 label + 关联（来源 PR/commit/上游 issue）+ **修复接力节**
   （含开工前置指令：「第一步重放复现命令——仍红→开工；变绿→回写
   issue『疑似已修复』而非闷头实现」）。

## 阶段 6：生命周期回写（issue 是活文档）

- 下游证伪了档 1 假设 → 划掉对应假设、记录新证据、必要时标
  「定位待重审」；
- 复现命令状态变更（跑不红/跑不绿）→ 同步进正文；
- 修复 PR 必须 `Closes #N` 关联——issue 的死亡由 PR 触发，不是手工关闭；
- pr-review-loop 的落档 finding → 本 skill 入口 c，形成闭环。

## 全局纪律

- 管生不管接：issue 建好即止，下游经「修复接力」节手动发起；
- 转述即污染：报错/日志贴原文，不写「报错说大概是什么」；
- 查重结论、定位档位、裁决标注——三个不可省的元数据；
- 用户 AFK 不阻塞：推荐生效 + 标注降级，诚实优于等待。
