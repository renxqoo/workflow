# 从问题到可交接的 issue

issue 的价值在于准确描述问题、证据和验收条件，让没有本次对话上下文的接手方可以继续工作。发现问题本身不触发发布流程，也不因另一个 skill 提到建票就自动发布。

## 1. 明确产物与授权

- 用户明确要求创建 issue/建票/记录为工单时，按指定或可从仓库确认的目标准备并发布；已明确建票不反复要求同一确认。
- 用户要求草稿、整理发现或尚未授权发布时，只产出草稿/报告。无发布授权不创建 issue、不追加评论；不能将用户未回应视为同意。
- 修改已有 issue、追加评论、拆出多张工单均应处在本次授权范围内。查重发现已有覆盖时，只有本次明确允许更新/补充已有工单才执行；仅授权创建时，交付已有链接和补充草稿，不自行评论、不重复建票。其他可交付工作继续完成。
- 读取目标仓库 AGENTS、issue 约定和已有工具；只使用可用且有权限的工单渠道。不依赖某个 CLI 或特定平台。缺少发布工具/权限时交付完整草稿并说明未发布。

本 skill 定义问题，不接管产品修复、Git 提交、push、PR 创建、自动修复接力或关闭工单。其他实现/验证 skill 仅在可用且本次任务需要时作为可选手段，不强制形成发布闭环。

## 2. 查重与选择工单形态

发布前搜索相关 open、近期 closed 工单和关联 PR，结合复现条件与根因判断是否覆盖。closed 工单再次出现同一症状可能是复发，保留历史。记录查过的关键词、对象和判定；访问不到则说明查重未完成，不声称无重复。

同根因的多种表现通常合并；只有可独立交付且用户范围需要时才拆票，不为了模板制造父子层级。按 bug、feature 或 tech-debt 选择 [issue 模板](references/issue-templates.md)，小问题使用轻量骨架。

## 3. 证据与定位

对 bug 使用 [定位纪律](references/locating.md)：

- **档 2，已复现**：实际执行过复现且看到目标症状，附命令、环境、期望与实际输出。
- **档 1，静态定位**：代码、日志或调用路径支持怀疑，列证据支持的假设和各自可执行的证伪条件。可以只有一条，也可以多条，不凑数量。
- **档 0，纯现象**：尚无定位，保留用户现象、已尝试手段与限制，说明缺什么。

复用对话、审查台账和现有测试证据，但核实版本、环境及来源。别将“我跑过”的转述直接升级为亲自复现。对 feature/debt 描述现状、影响和验收，不要求不存在的 bug 先红。

优先使用目标仓库已有复现/测试方式，选择成本合适的手段。只读或草稿任务不授权修改产品；复现可能写数据、用凭证或产生费用时先核对本次权限和隔离条件。定位到下游无需重新确认问题存在即可，不展开无预算的巡检。环境不可得时降档并交付已有证据。

## 4. 只澄清会影响结果的缺口

代码可检索事实先查；必要的环境信息和目标行为歧义再问用户。使用 [澄清纪律](references/clarifying.md) 记录已确认选择、合理假设和待决项。

用户已说明的场景、边界和验收直接使用，不按清单再问一次。非关键实现选择可在既有授权内采用合理默认并标注依据；影响外部契约、验收或发布权限的未决项不能靠沉默补成同意。缺少关键事实时保持草稿，继续独立可做的查重和证据整理。

## 5. 零上下文检查与发布

检查接手方能否仅凭正文理解：现象/目标是什么，证据处于哪档，怎样复现或证伪，哪些行为算完成，哪些选择已确认，哪些仍未知。保留必要的稳定接口和行为描述；源码证据可附提交固定的永久链接，不禁止可追溯引用，也不把浮动行号当规格。

脱敏后提供精简正文。报错/日志保留关键原文和来源，删掉凭证、个人数据和无关大输出。复现命令应能重放，不能依赖本机私有路径或隐藏对话背景。

在本次明确发布授权内，按渠道约定创建 issue；补充已覆盖工单需要本次明确的更新/评论授权，不能把创建授权转换成留言。已有对应授权不再要求形式确认。没有授权、目标仍不明确、关键行为未决或工具不可用时交付草稿并说明未发布。返回实际链接及做过的外部动作；发布结果未知时先核对已有对象再重试，避免重复工单。

发布不等于修复。后续新证据、状态回写和关闭只在用户后续授权或本次明确授权范围内执行，不自动评论、改票、建 PR 或安排下游任务。
