# issue 模板：一骨架 + 三类型差异

骨架来自成熟的 agent 任务简报实践（durability over precision / behavioral
not procedural / complete acceptance criteria / explicit scope boundaries
四原则），三类型共用骨架，差异只在各节的填充语义。

## 耐久性纪律（写任何一节之前先读）

issue 可能躺几周才被开工，代码会动。写得耐久：

- **写**：接口、类型、行为契约、错误码、配置形状、领域词汇；
- **禁**：文件路径、行号、「当前实现结构」假设——它们会腐烂；
- **例外**：复现命令里的路径是命令的一部分，允许（命令失效本身就是
  有效信号，触发下游回写）。

## 轻量变体（小修复形态）

判据对齐 feature-dev 小级：1-2 个文件、无外部契约面、修复行为一眼
可见。满足则用三节轻量骨架，全量骨架的其余节按需：

```markdown
# <现象一句话>
## 现状
<证据 + 复现命令（小问题常直接档 2）>
## 期望
<修好后的行为，一两句>
## 验收标准
- [ ] <可验证断言>
```

裁决记录/拆票/范围外通常省略（无方向性决策、无拆分必要、范围就是
现象本身）；元数据节照常保留。**跨会话开工的仍加修复接力节**
（重放/Closes #N 等契约见该节）。入口 b（对话沉淀的小发现）是轻量
形态的高频源。

## 骨架（三类型通用）

```markdown
# <标题：现象/需求的用户语言，一句>

## 现状（Current）
<bug：坏现象 + 证据链；feature：现在怎么办这件事的基线；
 tech-debt：当前的痛——每次碰到都要多花什么成本>

## 期望（Desired）
<行为描述，不写实现步骤。bug：修好后的行为；feature：用户故事；
 tech-debt：目标形态 + 为什么是现在（动机节，tech-debt 强制）>

## 证据与定位
<定位档位 + 按档位的内容，格式见下>

## 验收标准（Acceptance criteria）
- [ ] 每条可独立验证的行为断言（不是「工作正常」）

## 范围外（Out of scope）
- 显式列出不做的事——下游方案文档「不处理清单」的原始输入

## 裁决记录
- [用户裁决] <问过用户的决策，含选项与理由>
- [默认裁决，可否决] <按默认处理的决策 + 默认依据>
- [环境事实，来源：用户] <用户提供的环境信息：日志摘要/指代澄清/基线数值>

## 修复接力
> 修复由接手方发起（用户指令或编排 agent 自动接管），按本节指引
> 执行（feature-dev 流程）。
> 开工第一步：重放「证据与定位」节的复现命令——仍红→开工；
> 变绿→回写本 issue「疑似已修复，待验证关闭」，勿直接实现。
> 裁决记录：`[用户裁决]` 项直接引用不重问；`[默认裁决，可否决]`
> 项给一次否决窗口。
> 复现命令非测试形态时（curl/CLI/重放脚本）：测试计划第一项就是
> 把它测试化，接缝选择即测试口径的起点。
> PR 描述含 `Closes #N`。
> 修复过程中证伪了档 1 假设或发现复现命令状态变更 → 回写本
> issue（划掉假设/同步状态）。
> （档 0/档 1 issue 无复现命令时，先自行定位到可开工状态
> ——定位深度参考该 issue 的假设清单。）
```

## 类型差异

### bug

- **现状**：坏现象 + 完整证据链（触发路径、环境、expected/actual 对照、
  报错**原文**——转述即污染）；
- **证据与定位**（三档格式）：
  - 档 2：`定位档：2（已复现）` + 复现命令 + 期望红/实际红的输出摘要
    + 最小化说明（砍到每个要素都承重）；
  - 档 1：`定位档：1（静态定位）` + 排序假设列表（≥3 条，每条
    「若是 X，则改 Y 应使现象消失」格式）+ 疑似位置的行为描述
    （不写路径，写「定义 XX 错误码的模块」）；
  - 档 0：`定位档：0（未定位）` + 已尝试的定位手段与各自失败原因，
    含「缺什么才能到下一档」（给下游/用户的行动项）；
- **验收标准**必含一条：回归用例在旧实现上失败（复现命令的测试化；
  非测试形态的复现命令，测试化归属见修复接力节）。
  豁免判据：修复本身即删除死配置/无行为面时豁免——回归用例只对
  **行为面**修复强制，为单实例修复造类级守卫是过度工程；

### feature

- **现状**：现在用户怎么办这件事（没有此能力时的 workaround）——
  这是方案「不处理」边界的参照系；
- **期望**：用户故事（谁、在什么场景、要完成什么、为什么）；
- **证据与定位**换「影响面探查」：动哪些模块的行为、有无既有能力可
  复用（复用判断写行为不写路径）、新增的外部契约形状；
- **验收标准**从用户视角写（可演示的行为），不从实现视角写。

### tech-debt

- **现状**：当前的痛要**具体**——「每次加新端点都要在 3 处复制配置」
  优于「配置管理混乱」；
- **期望**：目标形态 + **为什么是现在**（动机节强制：即将到来的
  扩展/最近的踩坑/维护成本曲线）——没有时机的债务清理不如不建；
- **验收标准**：清理完成的可验证状态（如「新端点只需声明一处配置」），
  且行为不变（债务清理不改行为——改了就是 feature）。

## 元数据节（正文末尾，小字）

```
> 来源：<入口类型 + 触发上下文一句话>（AFK 发布时附：未确认发布——
> 澄清与裁决均按推荐默认生效，回查裁决记录节）
> 查重：<搜过的关键词 + 「无相近 issue」或「与 #N 相邻但不同，因为…」>
> 拆票：<无 / 父 issue #M 的第 N 切片，blocked by #K>
> 证据级：<直接记录 / 由台账动词反推（入口 c 旧格式台账时）>
```

## 拆票格式（仅大级需求）

父 issue：问题定义 + 验收总纲 + 子 issue 列表（链接）。
子 issue：垂直切片（每片完整穿透涉及的层、可独立演示/验证）、
`Blocked by: #<前置切片>` 显式标注、切片规模以「单个会话可完成」为限。
切片准则：先做让后续变容易的预制清理（若有），再按依赖顺序切。
