# 澄清机制：前沿轮询 + 裁决标注契约

澄清的目的不是问得多，是**下游不再重问**。feature-dev 有自己的需求
澄清阶段——本 skill 问过并落档的决策，下游见标注即跳过；没问的模糊，
下游会把用户重新拉回来。所以：要么问到、标好；要么按默认处理、标注
可否决。不允许第三种状态（留模糊且无标注）。

## 事实 vs 决策（先三分再行动）

- **代码可检索事实**（代码/日志文件/配置/历史能答的）：**永不问用户**。
  grep、read、跑命令自己查。把「这是什么行为」拿去问用户，是把检索
  成本转嫁给最贵的信息源；
- **环境事实**（仅用户或环境持有）：生产日志、特定环境的观象、
  「XX」指哪个进程/服务、期望的基线数值——代码里没有答案，但也不是
  决策。**要问，标注 `[环境事实，来源：用户]`**——它与决策的区别：
  有客观真相，问一次即定，无需推荐答案；
- **决策**（期望行为、优先级、不处理边界、验收口径）：问用户。这类
  问题没有代码里的答案，猜了就是埋雷——「时区显示不对，期望访客
  时区还是固定 UTC？」不问，下游方案必然二选一赌一把。

## 前沿轮询（怎么问）

把待澄清决策组织成依赖树，**前沿** = 前置已决、现在就能问的决策：

- 一轮问完整个前沿（编号 + 每题带**推荐答案** + 一句理由）；
- 用户答完一轮，前沿外推，再问下一轮——依赖未决的问题不许提前问
  （答案可能被上游推翻）；
- 推荐答案用你的代码库探查支撑（「仓库其他列表页都是分页的，推荐
  本页也分页」），不是拍脑袋。

```
❓ Q1 - <决策标题>：<题面，含选项>
   ➡️ 推荐：<X>——<一句依据>

❓ Q2 - …
```

## 裁决标注契约（本 skill 与下游的免重问协议）

issue 正文「裁决记录」节，两种标注、语义精确：

- **`[用户裁决]`**：本 skill 问过、用户明确选择。下游 feature-dev
  **不得重问**，方案直接引用（修复接力节自携本规则）；
- **`[默认裁决，可否决]`**：没问（用户 AFK / 成本不值），按推荐默认
  处理。下游知道这里有否决窗口——方案落档时给用户一次否决机会即可，
  不必单独提问。

标注对象：只标**方向性决策**（影响契约形状/边界/验收的）。风格级
小决策（文案措辞之类）不标，不值得下游看。

## AFK 降级

用户不在时全部决策按推荐答案生效，全部标 `[默认裁决，可否决]`，
issue 标「未确认发布」——诚实标注优于阻塞等待。用户回来后任何
一条被否决，回写 issue 即可（裁决记录节是活的）。

## 问什么：最小问题集

按类型的必问点（前沿轮询的起点，非全集）：

- **bug**：期望行为有歧义时必问（expected 不明确 = 验收标准写不出）；
- **feature**：三点必问——用户故事的核心场景 / 不处理边界 /
  验收的第一直觉（用户觉得「成了」长什么样）；
- **tech-debt**：为什么是现在（动机缺失 = issue 不该存在）。

其余一切先查事实，查完剩下的分叉才是问题。
