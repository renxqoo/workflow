# TDD

把需求或缺陷转成可执行的行为约束，再实现到通过。测试应表达独立的业务规则、外部契约或明确算例，不能照抄实现。

## 工作流程

1. 核对目标项目的 AGENTS、测试配置和邻近用例，确定预期行为、当前行为与最小可观察入口。使用项目已有测试设施。
2. 选择能观察目标行为的测试层级。单元、组件或集成测试都可以；跨进程、存储或浏览器行为需要在相应边界验证，不能只用 mock 声称已覆盖。
3. 先写一个能暴露缺陷或缺失行为的用例。期望结果来自独立需求或算例；不要仅断言常量等于声明值、复制静态对象，或用被测逻辑计算期望值。
4. 在修改实现前运行该用例，确认它因预期症状失败。若已经通过、无法执行或失败原因无关，先修正复现与测试环境。
5. 修复已证实的根因或实现目标行为，采用最小充分改动；只有现有结构阻碍正确实现时才重构。
6. 重跑用例，确认修复后通过，再运行受影响的邻近测试及项目要求的门禁。每次增加行为约束都重复这一循环。

测试应在行为错误时失败，在保持行为的内部重构后继续通过。名称说明症状或行为，避免绑定私有函数和调用顺序。涉及时间、随机数或异步任务时，控制输入与执行条件，并清理测试资源。

## 无法自动化时

先查找现有回归入口，不因测试昂贵或路径不熟就跳过项目要求。可以用定向脚本、浏览器操作或集成检查形成可重复证据，但必须说明它覆盖什么、没有覆盖什么，以及复现步骤和实际结果。

若目标项目要求自动化回归而当前无法完成，明确报告阻塞与尚缺的验证；替代检查不能被写成自动化门禁已通过。不得为过门禁删除断言、增加 skip、放宽预期或降低阈值。

## 交付证据

报告失败前与通过后的命令、症状和结果，以及执行的邻近验证。未取得失败前证据时直接说明原因。按项目要求报告真实用例数和覆盖率，不把测试通过等同于覆盖率达标。
