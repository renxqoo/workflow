# 系统性验证与验证装置

验证消费方实际使用的交付物，重点覆盖装配、跨边界、构建形态和替身漂移。结果是可以重放的行为证据与明确的验证限制，不能承诺“没有 bug”。

## 1. 模式、范围与实际门禁

- **系统性验证**：用户要求深入排查/验证某功能时，以其范围列必要的缺陷假设，参考 [缺陷假设与分层](references/bug-hunting.md)。没有可信触发路径的怀疑先核实，不自动生成测试或工单。
- **装置建设**：用户明确要建或补验证装置时，先盘点再填缺口。已有测试能驱动目标时只包装描述和补映射；没有合适装置才建最小必要装配，不另起平行框架。
- **装置维护**：用户要求处理地图漂移、驱动失灵或审计装置时，参考 [维护流程](references/maintenance.md)，区分文档漂移、装置缺口、环境阻塞和真实产品缺陷。
- 普通单元测试或一个已知 bug 的回归直接用项目现有测试，不展开全目录巡检或自动建装置。只问“改了 X 跑什么”时查已有映射和脚本即可。

读取目标仓库 AGENTS、实际脚本、测试配置、CI 和已有测试，确定运行时、依赖、门禁与权限。命令和阈值以目标项目为准；不硬套固定门禁数目，不猜脚本，也不降低现有检查。

验证授权不自动包含产品修复、提交、push、建 PR、发布 issue、CI/定时任务变更或真实服务调用。已有明确授权按范围执行，不重复询问。没有某个宿主工具时使用当前可用等价能力；无法运行时提供设计/静态证据并标注未执行，不把草稿称为可用装置。

## 2. 盘点已有资产

按本次范围读取：

1. e2e/旅程目录及已有单测、集成测试和 fixture；
2. 可编程假上游、隔离数据、时钟/随机源和测试 kit；
3. 真实进程、浏览器/终端驱动、冒烟脚本与清理函数；
4. CI/package 等脚本已定义的分门与选择性跑法；
5. 已有验证文档、改动面映射及证据目录。

记录每项的位置、驱动对象、证据和现有门禁归属。优先复用原入口，不搬家或重定义语义。共享状态不能隔离时串行驱动或拒绝双开，不因 Git worktree 隔离就假设外部服务也隔离。

按 [仓库访谈](references/interview.md) 核实交付什么、怎么启动、怎么驱动、能观察什么、如何隔离。不从目录名猜交付物，不预设 Web、monorepo 或某种语言。关键产品选择/资源条件代码答不了时再问。

## 3. 假设分层与测试设计

先确认外部契约和可观察目标，再列与本次功能相关的输入、状态、并发、资源、权限、序列化风险。每个候选记录依据、触发条件、后果和适合的验证层；证据不足的保持待核实，不为凑类别制造用例。

把假设分给最便宜且能覆盖实际风险的一层：纯规则/边界通常单测，装配/中间件/跨进程/产物差异通常集成或旅程。已有有效用例不重复写，不能用 e2e 重做全部单测矩阵。

期望值来自独立规格、人工算例或明确契约；不要抄实现输出、常量声明或用被测逻辑计算期望。已证实 bug 的回归应先观察缺陷失败，再由获授权的修复流程验证通过；非 bug 的契约测试允许起初就绿，无需制造缺陷。无法取得缺陷前失败证据时记录原因和实际证据，不伪造红灯。

未覆盖/无法证伪的怀疑与环境阻塞如实报告，不凭怀疑无限扩展用例或自动建票。修复产品缺陷只在本次明确修复范围内进行，否则交付发现和可重放证据；可用的实现或工单 skill 仅作为用户所需的可选后续。

## 4. 建设或补齐装置文档

沿用仓库已有验证文档位置，无约定时可用 `verify/`。结构参考 [装置文档模板](references/harness-doc-template.md)，功能地图参考 [地图格式](references/feature-map-format.md)。只写本次有用的信息：

- launch：真实启动命令、就绪条件与前置依赖；
- doctor：只读健康检查及判定边界；
- drive：现有测试/真实消费方路径的精确用法；
- evidence：动作、结果和适用的副作用证据；
- cleanup：只清本次持有的实例/资源，保留证据；
- 改动面 → 用例/旅程 → 证明内容的映射与未覆盖范围。

记录现有默认/冒烟/真实依赖测试的运行规则，缺某类时写清，不为了凑三门创建新框架。确定性协议假体放在现有外部边界；不为测试往产品增加专用后门。

真实凭证、真实服务、付费/生产数据或发送消息的路径，仅在**本次明确授权且资源与隔离条件具备**时运行；凭证存在不代表授权。其余情况使用已有假体或标注未覆盖，不自动接入 real 门。

旅程的确定性、假体校验和 flake 处置见 [旅程设计](references/journey-design.md)。证据脱敏与保留见 [证据纪律](references/evidence.md)。

## 5. 验证装置与交付

按新写的真实命令执行一条代表性功能或本次改动对应路径：启动 → 健康检查 → 驱动 → 捕脱敏证据 → 清理 → 核对证据仍存在且资源已释放。失败尝试也执行清理，不碰其他实例。

检查原有目标项目门禁，不擅自修改 CI、添加 nightly/real 定时任务、把 flake 移出默认门或降低阈值。发现门禁设计缺口时给出证据和建议；只有明确授权修改门禁时才实施，并继续保留未解决失败的可见性。

报告实际执行过的命令、结果、用例数与适用覆盖率，区分假体/真实依赖、源码/构建产物、成功/失败/未执行。文档或设计未实跑应称为未验证草稿，环境失败不能包装成通过。仅在本次允许编辑文档时补 AGENTS 的指路；不自动提交、建 PR、发布、建票或调度下一次执行。
