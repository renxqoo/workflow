# 验证装置：猎虫、生成、自证、防腐

## 为什么需要这个 skill

找 bug 和建装置是同一件事的两面：找到的 bug 要有地方被杀（装置），没有 bug 假设的装置是空转，没有装置的 bug 假设是纸上谈兵。所以本 skill 同时管两件：

**第一面：猎虫（哪里会坏）。** 给定一个功能或改动，按六类缺陷目录假设驱动地枚举 bug 假设，分层裁决后写成测试。目录见 `references/bug-hunting.md`：输入域（边界/三空态/类型/编码/畸形）、状态机（非法转换/重复触发/不变量守恒）、并发时序（竞态/交错/部分失败/取消）、资源生命周期（泄漏/崩溃恢复/优雅退出）、安全（越权/注入/重放/密钥泄露）、契约兼容（词表封闭/序列化往返/分页）。

**第二面：装置（在哪杀）。** 测试要跑在组装后的真交付物上才有意义。装置抓四类只有动态观察才能抓到的缺陷：

- **装配缺陷**：每个模块单测都绿，错在 env 没传到、迁移没跑、依赖顺序反了——这些只在组装后才存在；
- **接缝缺陷**：跨进程协议与真实中间件的时序；
- **形态缺陷**：测的是源码，用户跑的是 dist/打包产物，两者行为可以不同；
- **替身漂移**：mock 答应了真实依赖不给的行为。

一句话：**单测证明零件对，装置证明整机在消费方手里转。** 两面合起来才是「尽量减少 bug」的完整链条：假设驱动地找（猎虫），在真交付物上杀（装置）。

装置的产物不是「绿」，是把「行为正确」从断言（开发者写的）变成观察（装置在真实形态上执行的）。断言可以被写错，观察不会说谎。

## 0. 模式判定（进入即做）

| 入口 | 走向 |
| --- | --- |
| 要找 bug / 写测试 / 彻底测某功能（不管有无装置） | **猎虫模式**（§0.5）：`references/bug-hunting.md` |
| 仓库已有本 skill 生成的装置（`verify/` 或仓库约定位置） | **维护模式**（§6） |
| 无装置，用户要建 / feature-dev §7 判定「没有装置」 | **生成模式**（§1-§5） |
| 装置失灵：doctor 不过 / 旅程全挂 / 地图指向不存在的文件 | 维护模式，先做三分类诊断（§6 步骤 4） |
| 只想知道「改了 X 该跑什么」 | 不进本 skill：直接读 `verify/features/` 顶部的改动面映射表 |

## 0.5 猎虫模式（找 bug / 写测试时走这里）

完整程序见 `references/bug-hunting.md`，骨架：

1. **列表面**：读功能/改动，列出六张清单——输入面、状态面、并发面、资源面、权限面、契约面；
2. **过目录**：六类缺陷目录逐类过，每个可疑点写成一句 bug 假设（「并发提交会双扣费」），标注哪层杀。宁多勿漏：假设错了浪费一个用例，漏了放走一个 bug；
3. **假设转测试**：单测层的表驱动（一类假设一张表），装置层的旅程（终态断言 + 副作用断言，遵守 journey-design.md）。仓库还没有装置时先走生成模式建最小装置——旅程需要一个能跑的地方；
4. **红先行**：修 bug 前测试必须先红（跑在旧实现上失败），否则测试没牙。找到的 bug 走 to-issue 定位加工 + 回归用例入库；
5. **绿≠完**：杀不死的假设记进 issue（「怀疑 X，构造不出触发条件」），不假装测过。

与 feature-dev §3 的关系：那边是新功能写实现前定口径，这边可独立用于存量代码的深度猎虫；两边共用同一套六类目录。

## 核心信念

**假设驱动，红先行。** 「写几个测试看看」找到的是顺手能想到的 bug；先枚举假设再逐个证伪，找到的是目录里每一类的 bug。测试跑在旧实现上必须先红，否则它没在验证任何东西。

**分层裁决。** 每个假设分配给能杀死它的最便宜层：边界/编码/状态机矩阵 → 表驱动单测（微秒级，扫得起笛卡尔积）；越权/崩溃恢复/接缝时序 → 旅程（只有组装后的系统能暴露）。用 e2e 扫边界矩阵在经济上不成立，用单测测权限链路在结构上不成立。

**复用已有资产优先。** 大多数仓库已经有零散的 e2e 脚本、测试 kit、假依赖。另起炉灶意味着两套装置并存、断言语义漂移、维护翻倍，所以盘点包装是第一步，从零建是空仓才走的例外路径。

**确定性协议级假体优于真实依赖。** 能脚本化的外部边界（LLM 上游、邮件、hub 协议）就脚本化：时序确定、零成本、可断言。假体放在生产边界已有隔离的地方，模仿真协议，不 mock 内部函数——mock 内部实现等于测了 mock 而不是测了系统。真实凭证/花钱的场景走 opt-in 的 real 门，不进默认门禁。

**没跑过的装置是草稿。** 装置文档写完不算交付，用它逐字驱动一个功能跑通才算。理由很实际：agent 会照抄文档里的命令，对着坏基线或没验证过的步骤写的装置会教错每一次执行。

**装置会腐化。** 功能地图描述的功能没了、驱动路径变了、坑过时了。防腐不是额外负担，是装置生命周期的一部分——没有它，三个月后没人再信地图，装置退化成摆设。

**旅程质量决定门禁可信度。** 确定性不是口号：固定时钟、种子 RNG、轮询就绪、run-id 隔离；flake 有三级处置（唯一复现判定 → 隔离道不删断言 → 预算 5% 触发根治）；假体自己也会漂移，real 门复跑核心旅程是探针。完整纪律见 `references/journey-design.md`。

## 1. 资产盘点（生成模式第一步，也是与「从零写 e2e」的分界线）

按优先级扫五层，产出资产清单（每项记：位置 / 驱动什么 / 证据形态 / 进哪道门）：

1. **e2e / 旅程目录**：`e2e/`、`packages/e2e/`、`*/journey*`、`*.e2e.ts` 及语言等价物；
2. **测试装置 kit**：隔离 schema 装配、脚本化假上游/假依赖（`fake-*`、`upstream.ts`、`kit.ts`、`harness.ts`）、种子数据脚本；
3. **驱动脚本**：CDP/Playwright/PTY 驾驶、冒烟脚本、`scripts/` 下的验证入口；
4. **门禁结构**：CI workflows 与 package scripts 里的 e2e/real/smoke 分门证据——多份测试配置说明已有分门实践，如实继承，不重造门；
5. **AGENTS.md / README 的验证节**：既有验证纪律（选择性跑规则、real 门规则）是装置的一部分，搬进文档而不是重写。

已有资产**包装描述 + 指路**，不搬家不改语义。理由：搬运已有装置等于改门禁语义，必须显式裁决（迁移场景走 repo-migration 的装置搬运纪律），不许顺手搬。盘点发现的缺口（无 doctor、无选择性跑映射）在生成时补上。

完全空仓才建**最小装置**（隔离数据区 + 一个可编程假体 + 一条全链旅程），一次性投入换所有后续功能复用。

## 2. 仓库访谈五问（问代码不问人）

**锚点是「交付物」（deliverable），不预设目录形态。** 仓库用什么目录组织是它的自由，装置只关心「仓库声明它交付什么给谁」。探查手法见 `references/interview.md`。

| 问 | 答案决定什么 |
| --- | --- |
| **Deliverable**：交付什么给谁 | 驱动配方选型与装置主次；消费方定义验证视角 |
| **Run**：怎么本地启动到可驱动状态 | launch 节：端口、env、种子、鉴权、就绪信号 |
| **Drive**：agent 怎么程序化驱动 | 既有 harness 优先，其次按交付物形态选通用配方 |
| **Observe**：能捕什么证据 | evidence 节：截图、transcript、响应体、日志、退出码、DB 状态 |
| **Isolate**：两实例能否并行 | 隔离策略；不能并行则显式声明「拒绝双开」——拒绝双开好过污染会话 |

**基线检查**：checkout 跑不起来（构建失败/启动即崩）→ 先修或精确报告，不许在坏基线上生成装置。

代码答不了的才问用户（多交付物优先级、real 门凭证归属、不可并行时选拒绝双开还是排队锁），攒批用 AskUserQuestion。

## 3. 生成装置文档 + 功能地图

**装置文档**（`verify/SKILL.md`，仓库另有约定从其约定）骨架见 `references/harness-doc-template.md`，必含：

- **五节**：launch（就绪信号与拆除）/ doctor（一条只读健康检查）/ drive（本仓库真实句柄，不是示例语法）/ evidence（证据标准与存放点）/ cleanup（只杀自己启动的，按句柄不按进程名）；
- **三门**：

| 门 | 内容 | 进默认门禁 |
| --- | --- | --- |
| 默认门 | 确定性假体旅程，断言业务终态（对账/一致性，不只是 200） | 是，按改动面选择性跑 |
| 冒烟门 | 双形态冒烟（源码形态 vs 构建/打包产物形态） | 手动/发布前 |
| real 门 | 真实凭证、真花钱的上游 | 否，opt-in |

- **改动面映射表**：改动面 → 必跑旅程 → 证明什么。这是装置的操作界面：feature-dev 收口、pr-review-loop 组路、「改了 X 跑什么」都查它。没有这张表，装置只能全量跑或凭感觉跑，全量跑太贵导致最后没人跑；
- **旅程按 journey-design.md 的纪律写**：确定性技术、旅程级反模式（不走 test-only 后门、不复刻单测、断言终态副作用）、种子数据所有权、假体保真三防线。生成装置时新写的旅程遵守它，盘点发现的既有旅程不达标也不急着重写——先把它们挂进映射表，重构旅程走 feature-dev（装置也是代码）；

**功能地图**（`verify/features/`）格式见 `references/feature-map-format.md`：README 索引 + 每个消费方可感功能一个文件，四节固定（是什么 / 怎么到达 / 怎么驱动 / 坑）。消费方按交付物定义：服务的消费方是 API 调用者，库的消费方是 import 它的开发者。初始覆盖 top 3-5 个功能即可，地图是生长物。副作用必须单独断言（文件写了/行插了/消息发了），「界面看起来对」不构成证明。

## 4. 自证（不过不算交付）

按刚生成的装置文档**逐字执行**一遍：

1. launch → doctor → 驱动**一个**地图功能（一个就够，地图的存在就是让后续跑其余的）；
2. 捕证据（脱敏先于落盘，见 `references/evidence.md`）→ cleanup → **确认证据在声明位置仍存在**。cleanup 吃掉证据 = 自证失败——这一步在防「清理逻辑顺手删掉证明目录」的真实事故；
3. 每次失败迭代后同样跑 cleanup，别让失败尝试遗留进程和端口。

## 5. 接线

- AGENTS.md 加一行指路（「验证装置与改动面映射见 verify/」）；
- 旅程脚本入库（「不入库、每次重建」是反模式：重建的装置没有回归价值）；
- **CI 时机矩阵**：PR 时按改动面选择性跑默认门；nightly 跑默认门全量 + real 门（有凭证环境时）；发布前跑冒烟门（双形态）+ 地图活跑抽样。选择性的便宜和全量的置信各得其所；
- 流水线接力：feature-dev §7 无装置时先走本 skill；to-issue 的档 2 复现脚本沉淀进地图，成为该功能的驱动配方；pr-review-loop 的验证命令集可直接引用装置三门，不重复枚举；feature-dev §3 定测试口径时引用六类目录（bug-hunting.md），两边同一套词汇。

## 6. 维护模式（防腐审计）

以**功能**为粒度（不是逐句校对），全程只编辑装置自己的目录，**绝不改产品代码**。完整程序见 `references/maintenance.md`：

1. **索引卫生**：地图 README 与实际文件对账（缺/多/重/死条目）；
2. **源读波**：每功能一个只读子 agent，从源码回答「这个功能现在怎么工作」，标注疑似漂移（带引用），返回一条可执行的驱动配方；
3. **活跑波**：源码看着干净也要跑——协调者统一驾驶每个功能至少一次，守三条不变量（doctor 先于首驱 / 证据在 cleanup 后仍存活 / drive 起的东西不活得比 drive 久）；
4. **三分类处置**：描述错了→修地图（文档漂移）；功能在但驱动不了→修装置（装置缺口）；应用真坏了→走 to-issue，**不许在文档里把坏行为写成对的**——这条纪律防止「文档追随 bug 漂移」，把产品缺陷合法化；
5. 一个 PR 落地全部证明过的修正，走四门。

触发：功能大改合入后（对应条目）/ 发布前全量 / 装置失灵被发现。产出三态：clean / changed / blocked。

## 边界（本 skill 不管什么）

- **功能实现**：走 feature-dev，装置是它的地基；
- **性能/压测/基准**：时延、吞吐、资源预算属于基准纪律（跑分方法论 + 数字纪律），旅程只做行为断言。装置抓「行为对不对」，不抓「快不快」；
- **修产品缺陷**：装置发现缺陷走 to-issue，本 skill 从不修改产品代码。
