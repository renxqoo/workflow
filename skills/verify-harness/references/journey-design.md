# 旅程设计：确定性、反模式、flake 处置、失败取证、种子所有权、假体保真

装置的信任度由每条旅程的质量决定。本文件是写旅程时的完整纪律。

## 确定性技术（让「绿」可复现）

- **固定时钟**：时间从注入的 clock 拿，不读系统墙钟；断言行为（状态机推进），
  不断言真实时间差（「x 秒内完成」这类断言在慢机器上必 flake）；
- **种子 RNG**：任何随机性（乱序、采样、抖动注入）用显式种子，失败可重放；
- **轮询就绪，不用 sleep**：等待条件成立（端口应答/日志行出现），带上限轮询；
  固定 sleep 既慢又脆——快机器白等，慢机器不够等；
- **run-id 隔离**：每次运行生成唯一 run-id，数据/目录/schema 以它命名，
  杜绝并发与残留数据误断言；
- **唯一 ID 前缀**：旅程造的实体用可识别前缀（如 `e2e-`），断言和清理都能
  精确圈定自己的数据。

## 旅程级反模式

- **test-only 后门**：不经内部 setter、专用测试端点、仅测试编译分支验证——
  那是单测的事。旅程只走消费方真实路径；需要后门才能验证 = 装置缺口，
  不是给产品开后门的理由；
- **高成本单测复刻**：旅程断言的东西单测已覆盖 = 只加维护成本不加新信号。
  旅程的存在理由是跨接缝（进程边界、真实中间件、真形态产物），
  接缝内的行为留给单测；
- **断言中间态而非终态**：断言「请求返回 202」却不断言「行已落库、消息已发」
  = 没验证到副作用，接缝缺陷正好从这里漏过；
- **猜测式等待**：sleep N 秒后再断言，见确定性技术节，一律改轮询。

## flake 处置（三级纪律）

默认门的可信度 = 挂了就真的有事。flake 不处置，门禁沦为狼来了。

1. **先判定，不许上来就重跑**：旅程红 → 唯一复现（同旅程原地重跑一次），
   稳定红 = 按真缺陷处理（走 to-issue + 定位）；间歇红 = 疑似 flake；
2. **确认 flake → 隔离道（quarantine）**：旅程标记隔离 + 建 issue（附最近
   一次全绿/全红记录与触发条件），从默认门移到隔离道继续跑。
   **不许删断言、不许 skip 换绿**（feature-dev 假绿禁令同样适用）；
3. **flake 预算**：隔离道旅程数超过默认门的 5% → 这不是单条旅程的问题，
   是装置健康问题，进维护模式根治（时序竞争、隔离不净、资源争用、
   依赖真实网络）。

## 失败取证（旅程红时自动转储）

旅程红的那一刻是取证黄金期，重跑就没了。装置在断言失败路径上自动转储：

- 进程日志尾（各进程最后 N 行）；
- 当时的关键状态：DB 关键行 / 文件快照 / 假体 trace 文件；
- UI 旅程加截图（失败瞬间的，不是重跑后的）；
- 全部落 evidence 目录，文件名带 run-id，与成功证据同位置不同前缀
  （如 `fail-<run-id>/`）。

没有失败取证的旅程，定位成本翻倍——人只能靠回忆「刚才挂的时候什么样」。

## 种子数据所有权

- 种子由装置的 fixture builder 脚本**唯一产出**，旅程不许内联硬编码种子；
- 每个旅程在地图文件里声明自己需要的**最小**种子集，装置按声明装配；
- 种子脚本的修改与消费它的旅程改在同一个 PR——种子悄悄变，
  旅程的断言值就漂了。

## 假体保真（fake 会漂移）

假体答应的行为可能不再是真实依赖的行为：真实现改了协议细节、错误形态、
时序约定，fake 还在模拟旧版——默认门全绿，real 环境故障。三条防线：

1. **real 门复跑核心旅程**：挑 1-2 条最核心的旅程在 real 门用真依赖
   跑同一套断言。real 门挂而默认门绿 = 假体漂移的头号信号；
2. **有条件时 contract 双跑**：同一旅程套件对 fake 和真实实现各跑一遍，
   差异即漂移（上游有 sandbox/测试环境时适用）；
3. **假体变更与真实现变更同 PR**：协议升级时，fake 的实现对接方和
   fake 本身必须一起改，不许「先把 fake 留在旧协议上回头再补」。

## 边界：性能不在旅程里

装置验证功能行为。时延/吞吐/资源预算属于基准纪律（跑分方法论 + 数字纪律），
不进旅程断言；旅程里只允许行为断言，见确定性技术节的时钟条目。
