# 功能地图格式契约

`verify/features/` 下：README 索引 + 每个消费方可感功能一个文件。

## README 索引

顶部是改动面映射表（见 harness-doc-template.md），然后是功能清单：

```markdown
## Features

- [结算恢复](./billing-recovery.md)：崩溃/重启后账本对账归零，覆盖 hold→settled 全状态机。
- [会话流式渲染](./session-streaming.md)：思考流+正文流+工具执行在 UI 全链可见可排队。
```

每条一句话说清「验证什么行为」，让人不用打开文件就知道该不该读。

## 功能文件契约

每个文件以 H1 标题 + 一段消费方视角描述开头，然后**恰好四个 H2，顺序固定**：

```markdown
# <功能名>

<一段话：消费方视角的这个行为是什么。不写实现。>

## Sub-features

- <短 ID>：<一行一个可观察行为>

## How to get to it (user POV)

<每个消费方入口一条：从哪里进、点什么、输入什么。>

## Driving with <harness>

Preconditions:
- <种子数据 / 环境状态 / 假体就绪>

- **<消费方动作>** → `<精确命令>` → <可观察结果>。
- **<消费方动作>** → `<精确命令>` → <可观察结果>。

## Gotchas

- <会让一次验证运行白跑或作废的陷阱。>
```

## 写作规则

- **只写消费方路径**：路由名、ARIA 角色、命令名、菜单文案——这些是稳定句柄。
  组件内部状态、函数名、CSS 类名是实现的私有物，改版即漂移；
- **动作配命令配结果三连**：每个动作给出精确命令和「跑完后你应该看到什么」。
  结果要具体到可断言（「余额显示 4.20」不是「余额正确」）；
- **副作用显式断言**：动了持久状态的功能，地图里写明验证第二视角
  （DB 查询 / 文件读取 / 另一会话观察），「界面看起来对」不够；
- **命令逐字照抄**：引号、flag 原样；agent 会一字不差地执行；
- **不可达路径如实报**：前置条件不满足（无凭证/仅生产环境）时，
  「verified-unreachable + 尝试过的命令 + 缺的前置」是合法记录，
  不许假装从别的路径验证过了；
- **坑要具体**：「时区敏感，断言前先固定 TZ=UTC」有用；「小心边界情况」没用。

## 维护触发

功能大改合入、新功能走完 feature-dev 收口、或装置失灵被发现时，
对应条目进维护模式（见 maintenance.md）。地图条目的增删走同一个 PR
as 功能改动——地图和功能同生共死，不允许「功能删了地图还留着」。
