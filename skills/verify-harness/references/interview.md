# 仓库访谈：五问的代码探查手法

原则：**问代码不问人**。五问的答案 90% 在仓库里；只有代码答不了的
（产品意图、外部凭证约定）才问用户，攒批一次问。

**五问的锚点是「交付物」（deliverable），不预设目录形态。** 仓库用什么目录
组织（`apps/`、`packages/`、`src/`、单文件、无目录约定）是它的自由；
装置只关心「仓库声明它交付什么给谁」。

## 问 1：Deliverable（仓库交付什么给谁）

找**交付物声明**，每个命中都是一个候选交付物：

1. `package.json`：`bin`（CLI）、非 `private` + `exports`（可发布库）、
   `workspaces`（列出候选面再逐个下钻）；
2. `Dockerfile*` / `compose.yml`：镜像里跑什么 = 交付的服务；
3. CI workflows 的部署目标（部署什么 = 交付什么）；
4. `go.mod` 的 main package / `pyproject.toml` 的 `[project.scripts]` /
   `Makefile install` 等语言等价物；
5. README 的产品描述（「X 是一个……」通常已写明交付物与受众）。

产出：交付物列表 + 主次标注 + 每个的**消费方是谁**（API 调用者 / 桌面用户 /
敲命令的人 / import 库的开发者 / 下游仓库）。消费方定义验证视角：
装置替谁观察行为，地图按谁的 POV 写。

多交付物仓库（如「网关服务 + 管理台 + 客户端 SDK」）全部列出，
装置文档的 drive 节按交付物分小节。

## 问 2：Run（怎么本地启动到可驱动状态）

1. `package.json` scripts：`dev` / `start` / `docker:up` 一族；
   非前端项目找等价物（`make dev`、`go run`、`python -m`）；
2. `docker/` 或 `compose.yml`：all-in-one 启动是「一条命令起全栈」的证据；
3. `.env.example`：启动需要的 env 全集，逐个标注哪些是装置必须给的；
4. README 快速开始节。

**就绪信号**优先选机器可判定的：日志行（「listening on」）> 端口应答 >
健康检查端点 > 固定 sleep（最后手段，写明为什么没有更好信号）。

**降级链**（本地起不了全栈时）：in-process 装配（不拉起真进程，
同依赖全真装配）> 只起目标交付物 + 假依赖 > 纯静态检查。
降级形态在装置文档如实标注，不冒充全链。

**库交付物**的 Run = 「在消费方环境里被 import 并调用」：装置的形态是
消费方式的调用旅程（拿真实入口函数跑一条消费场景），不是启动进程。

## 问 3：Drive（agent 怎么程序化驱动）

**既有 harness 优先**：

1. e2e 目录里的 kit/harness/fake 文件——读它们怎么驱动，照抄接口；
2. 测试里的真实进程装配（spawn 子进程、CDP、PTY 的既有用法）；
3. 健康检查端点 / curl 可达的 API 面。

通用配方（既有 harness 不存在才按交付物形态选）：

| 交付物形态 | 配方 |
| --- | --- |
| HTTP 服务 | 直接 curl/fetch；断言响应体 + 副作用（DB 行、文件） |
| Web/Electron UI | CDP / Playwright；选择子用 ARIA 角色与可访问名，不用坐标 |
| CLI/TUI | PTY（tmux/expect 式）；断言 transcript 与退出码 |
| 库 | 消费方式调用旅程：真实入口函数 + 真实数据流过一遍 |
| 桌面/移动 | 调试端口 / 模拟器驱动（仓库已有的驱动 skill 优先） |

**假体的既有资产优先**：`fake-hub.ts`、`upstream.ts`、`captureMailer` 这类
脚本化假体是装置的核心资产，盘点时单独列出，写进 drive 节的「依赖假体」清单。

## 问 4：Observe（能捕什么证据）

探查：既有 e2e 断言什么，就证明什么。常见形态：

- 响应体 / 状态码（服务交付物）；
- 截图 + ARIA snapshot（UI 交付物）；
- transcript / 命令追踪文件（假体侧的只增日志 + 全文 grep 断言——
  「动作 + 结果态」双捕的范例形态）；
- DB 状态 / 对账查询（断言的不只是 200，是账平）；
- 退出码 / 日志行 / 函数返回值与副作用（库交付物）。

**证据标准**：捕「消费方动作 + 结果态」，不只捕最终画面；副作用必须单独断言
（文件写了 / 行插了 / 消息发了）。「界面看起来对」不构成证明。

## 问 5：Isolate（两实例能否并行）

- 端口是否可配（env 有 `PORT` 族变量 = 可并行）；
- 数据目录是否可指（`DATA_DIR` 族变量可注入 = 可并行）；
- 数据库 schema 是否可隔离（「隔离 schema + 全迁移链回放」是标准答案：
  每次运行独占 schema，跑完删）；
- 全局资源占用（锁文件、固定 socket 路径、宿主机 DNS 改写、固定调试端口）
  = 不可并行的信号。

不能并行 → 装置文档显式写「**拒绝双开**」+ 原因。拒绝双开好过污染会话；
多 agent 并行开发时这个声明是 worktree 之外的第二道隔离边界。

## 问用户的时机（攒批，AskUserQuestion）

只有这些代码答不了：

- 多个交付物里哪个优先建装置（产品阶段判断）；
- real 门用什么凭证约定（外部系统的账号归属）；
- 不可并行环境下「拒绝双开」还是「排队锁」（团队协作约定）。

每问 2-4 个具体选项，带后果说明。
