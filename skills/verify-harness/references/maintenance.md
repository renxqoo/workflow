# 维护模式：源读波 / 活跑波 / 三分类处置

装置会腐化：描述的功能没了、驱动路径变了、坑过时了。防腐审计以
**功能**为粒度（不是逐句校对），全程只编辑装置自己的目录
（verify/ 及其脚本），**绝不改产品代码**——产品缺陷走 to-issue，
装置审计没有改产品代码的授权。

## 产出三态（先声明走哪个）

- **clean**：每个功能都得到源码覆盖 + 活跑覆盖，无事可交付。无分支无 PR；
- **changed**：一个 PR 落地全部**证明过的**修正；
- **blocked**：覆盖没跑完或修不动，说清卡在哪。

## 程序

### 0. 定位目标

找装置文档与 features/。多个候选问用户；一个没有 → 不该进维护模式，
走生成模式（§1-§5）。

### 1. 索引卫生

README 索引与实际文件对账：缺条目（有文件无索引）、多条目（有索引无文件）、
重复、死链，轻量修掉。顺手扫近期 churn：新合入的消费方可感功能没进地图的，
列出来——有具体源码路径才算「缺失」，不猜。

### 2. 源读波（并行，只读）

每个功能文件派一个只读子 agent，回答「这个消费方可感功能现在怎么工作」：

- 返回：功能摘要 / 源码入口点 / 疑似漂移（带引用）或「无」/ 一条可执行驱动配方；
- 子 agent **不驱动应用、不编辑文件**——只读源码。理由：驱动共享实例的
  权限只归协调者，多个子 agent 同时驾驶 = 互相污染会话；
- 各返回收拢后合并重叠配方（多个功能共享一个实例状态就合成一态）；
- 引用的漂移抽查核实，不重证干净项。

### 3. 活跑波（串行，协调者统一驾驶）

**源码看着干净也必须跑**——源读只能证明「描述和代码一致」，不能证明
「装置真的驱动得动」。按装置自己的 launch 模型驾驶（长驻服务一个实例
串行驱动；短命 CLI 每次驱动独立会话），每个功能至少一次。
全程三条不变量，无论中间出什么错：

1. **doctor 先于首驱**；每次怪事后重跑 doctor；doctor 也看不见的卡死态
   （进程健康但 UI 楔死）→ 重置到已知态或重启，不赌运气；
2. **已捕证据在任何 cleanup 后仍存活**，到声明位置检查，不假定；
3. **drive 起的东西不活得比 drive 久**——失败残留同样清（共享实例清残留
   不清实例）。

### 4. 三分类处置（每个发现）

| 分类 | 判据 | 处置 |
| --- | --- | --- |
| **文档漂移** | 应用行为与地图描述不符，但应用本身对 | 修地图/装置文档 |
| **装置缺口** | 功能正常，harness 驱动不了它 | 修装置（配方/脚本/假体） |
| **产品缺陷** | 应用行为真的坏了 | 走 to-issue 建 issue |

**不许在文档里把坏行为写成对的**：把产品缺陷记录成「现状如此」等于
文档追随 bug 漂移，把缺陷合法化。doctor 失败先怀疑装置漂移：在编辑
权限内修，重试**一次**（只重启被修动作废的部分），再挂才 blocked。
harness 修好后必须**活跑重证**再入库。

### 5. 收口

changed → 一个 PR 装全部修正，合入前重读每个改动文件，走四门；
clean/blocked → 无 PR，如实报告。运行笔记（覆盖了什么 / unreachable 前置 /
确认的漂移 / 产出态）记在 scratch，不进库。

## 触发时机

- 功能大改合入后（对应条目）；
- 发布前全量（活跑波全功能）；
- 装置失灵被运行时发现（doctor 挂 / 旅程全红 / 地图指向不存在的文件）——
  先诊断三分类再动手，别把产品缺陷当装置漂移修文档。
