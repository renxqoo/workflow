# 证据纪律：脱敏、存放、真实性

## 脱敏（先于一切）

证据会入库、会被 PR 展示、可能被未来任何会话读取。捕证据时**先脱敏再落盘**，
顺序不可反：

- token、API key、cookie、Authorization header、密码 → `<REDACTED>`；
- 凭证只活在 env 里：装置从环境变量读凭证，截图/日志/响应体里不出现值；
  real 门尤其如此——它跑真凭证，产物里的 auth header 是最高危泄露源；
- 内网地址、个人路径按仓库敏感度裁量（开源仓库建议一并抹掉）；
- 捕大输出时只引用带信号的那几行，不整段转储。

**检验：证据目录值得直接贴进公开 PR，才算合格。**

## 存放与生命周期

- 每次运行一个 run-id 目录：`evidence/<run-id>/`，成功与失败证据同根；
- 失败证据前缀 `fail-`（`fail-<run-id>/`），见 journey-design.md 的失败取证；
- cleanup 清实例与临时态，**永不清证据**——证据是产出物，不是临时文件；
- 入库范围：小体积、脱敏过的关键证据（对账查询结果、trace 摘要）随 PR 走；
  大体积（截图全集、完整 trace）留本地，PR 引用路径；
- 证据带语境：每份证据配一行「这是哪条旅程、哪个断言、什么时间」，
  三个月后的读者（包括 agent）不该靠猜。

## 真实性标准

- 捕「消费方动作 + 结果态」，不只捕最终画面；
- 副作用单独断言：文件写了/行插了/消息发了，用第二视角观察
  （DB 查询、文件读取、另一会话），不信界面上那个对勾；
- 断言值可溯源：期望值来自 fixture 或规格文档，不是「跑一遍把输出抄下来」
  ——抄下来的断言锁死的是当前行为（含 bug），不是正确行为；
- dry-run/test 模式要用观察验证它真跳过了什么（文件/网络/git refs），
  有些 dry-run 仍然碰网络。
