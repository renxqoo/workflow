# 猎虫手册：六类缺陷目录与测试设计

本手册回答一个问题：**给定一个功能或改动，怎么系统性地找出它会怎么坏，并写出杀它的测试。**

两个前提立场：

- **假设驱动**：不是「写几个测试看看」，是先枚举 bug 假设（「这里并发提交会双扣费」），再为每个假设写一个能证明或证伪它的测试。绿只证明「这个假设不成立」，不证明「没问题」；
- **分层裁决**：每个假设分配给能杀死它的最便宜层。边界/编码/状态机 → 表驱动单测（微秒级，才扫得起矩阵）；并发/崩溃恢复/越权/接缝 → 旅程（装置层，只有组装后的系统能暴露）。单测杀不了的才上旅程，旅程不重复单测已覆盖的。

## 猎虫程序

1. **列表面**：读功能/改动，写出六张清单——输入面（每个入口收什么）、状态面（状态机的状态与转换）、并发面（哪里有共享可变状态、哪里有外部调用可重试）、资源面（开什么、什么时候关）、权限面（谁能碰什么、边界在哪）、契约面（对上下游承诺什么）；
2. **过目录**：下面六类逐类过一遍，每个可疑点写成一句 bug 假设，标注「哪层杀」。宁多勿漏——假设错了浪费一个用例，漏了放走一个 bug；
3. **假设转测试**：单测层的做成表驱动（一类假设一张表）；装置层的写成旅程（一段驱动 + 终态断言 + 副作用断言，遵守 journey-design.md）；
4. **红先行**：修 bug 前测试必须先红（跑在旧实现上失败），否则测试没牙。找到的 bug 走 to-issue + 回归用例入库；
5. **绿≠完**：全部假设被证伪后收口。还想更深：把杀不死的假设记进 issue（「怀疑 X，构造不出触发条件」），别假装测过了。

## A. 输入域（等价类与边界）

怎么想：每个输入字段问四个问题——合法值的边界在哪？类型错了会怎样？编码极端值过不过得去？畸形结构会不会崩？

- **边界值**：0、1、空、最小、最大、刚好超限一格（off-by-one 高发区：分页 limit、截断长度、重试次数上限）；
- **三空态**：`null`、缺字段、空字符串是三个不同的输入，很多代码只挡了其中一种；
- **类型混淆**：数字传字符串、负数进无符号语义、浮点当金额、超大整数丢精度；
- **编码极端**：emoji/组合字符、BOM、控制字符、超长字符串（上界处截断还是 500？）、非 UTF-8 字节；
- **畸形结构**：截断的 JSON、数组传对象、错误 content-type、嵌套深度爆炸；
- 怎么杀：全部表驱动单测。一张表一个字段，断言具体输出（`slugify("Hello, World!") === "hello-world"`），不断言「不抛错」。

## B. 状态机（转换与不变量）

怎么想：画出状态机（状态 × 事件 → 结果），逐格问三件事——这个转换合法吗？重复触发会怎样？非法转换被拒绝还是被静默接受？

- **非法转换**：终态后再触发（已删除的资源再删一次、已取消的订单再支付）；
- **重复触发**：同一事件两次（幂等吗？双扣费、双发货就在这）；
- **一次性事件恰好一次**：确认邮件发两次、审计日志写两条；
- **不变量守恒**：状态流转后，守恒量还守恒吗（余额 = 初始 - 流出；held + settled = 总额）——对账断言，不是单点断言；
- **卡死状态**：有没有只进不出的状态；异常路径进得去出不来吗；
- 怎么杀：转换矩阵表驱动单测（每个状态 × 每个事件一格）；不变量对账用旅程跑（真实账本跨进程才可信）。

## C. 并发与时序

怎么想：标出所有共享可变状态和所有可重试的外部调用，问「两个同时发生会怎样」「慢一拍会怎样」「中途断掉会怎样」。

- **竞态窗口**：双击提交、并发下单、check-then-act（先查余额再扣，两请求都过了检查）；
- **交错**：晚订阅（事件发完才订阅）、读到一半被写（游标失效）、乱序到达（后发的先到）；
- **部分失败**：第一步成第二步败——状态残留吗？回滚吗？还是卡在中间态？这是分布式 bug 的第一大本营；
- **超时与取消**：慢上游、客户端中途断开（服务端继续算完并扣费？）、取消传播到所有层了吗；
- **重试风暴**：上游 5xx → 重试 → 上游更慢 → 更多重试；重试带不带幂等键；
- 怎么杀：并发语义单测能 mock 交错的部分用单测；真进程并发、取消中途、崩溃恢复（见 D）必须是旅程。并发旅程要断言终态一致性（对账归零），不断言中间态。

## D. 资源与生命周期

怎么想：数资源句柄——进程、fd、连接、定时器、监听器、临时文件、锁。每个问：异常路径上它会被释放吗？进程死在半路会留下什么？

- **泄漏**：错误路径提前 return 跳过清理；重试路径每次新开连接不关旧；监听器只加不减；
- **崩溃恢复（混乱旅程）**：旅程中途 SIGKILL 主进程/断数据库连接/杀上游，重启后断言状态一致、无重复副作用。这是普通旅程给不了的置信，值得为核心链路（计费、提交、持久化）各写一条；
- **优雅退出**：SIGTERM 后还在途的请求怎么办？半写的文件怎么办？
- **背压**：队列满、消费者慢——丢弃、阻塞还是 OOM；
- 怎么杀：泄漏用单测（跑 N 轮量句柄数）；崩溃恢复和优雅退出必须是旅程（只有真进程能被杀）。

## E. 安全（滥用用例）

怎么想：换帽子——不问「正常用户怎么用」，问「恶意客户端怎么用」。每个入口过一遍：

- **越权（IDOR）**：把资源 id 换成别人的——404/403 还是 200 泄数据？每个「按 id 取资源」的端点都要过这关；
- **认证绕过**：无凭证、过期凭证、伪造签名、其他租户的合法凭证；
- **注入**：用户输入进命令行（shell 注入）、进路径（`../../` 遍历）、进模板/查询（SSTI/SQLi）；
- **SSRF**：用户给的 URL 服务端真的去 fetch？内网地址挡了吗；
- **重放与限流**：同一请求重放（幂等键挡吗）、高频刷（限流生效吗、绕过姿势呢——改 ip 头、并发分片）；
- **密钥泄露**：响应体、错误信息、日志、证据截图里有没有凭证（配合 evidence.md 脱敏，但先要测「产品自己不漏」）；
- **权限提升**：普通用户的入口能不能触达 admin 面（参数篡改、直接调内部路由）；
- 怎么杀：注入/输入类的表驱动单测；越权/认证/重放必须是旅程——权限链路只有穿过真实中间件才可信（mock 的鉴权永远通过）。安全旅程集中在攻击套件（Tillgate 的 attack.test.ts 是这个形态）。

## F. 契约与兼容

怎么想：找所有「两侧必须一致」的约定，问「一侧单方面变了会怎样」。

- **词表封闭**：导出枚举 == 文档词表 == 对端认识的集合；新增枚举对旧客户端是未知值；
- **判别联合穷尽**：consumer 对每个 variant 都有分支吗（编译器能查的让编译器查）；
- **序列化往返**：时间戳时区、浮点精度、金额（永远 Decimal）、大整数、undefined 字段序列化后还在吗；
- **分页与排序**：边界页（刚好一页、空页、最后一页多取一）、排序稳定性、游标失效；
- **协议版本**：旧客户端 × 新服务、新客户端 × 旧数据；
- 怎么杀：词表/穷尽用单测（甚至编译期）；序列化往返、版本兼容用旅程双形态（这正是形态缺陷的领地）。

## 与其它 skill 的分工

- feature-dev §3（测试计划先行）是「写实现前定口径」，口径里就应引用本目录生成测试面；本手册可独立用于**存量代码**的深度猎虫（没有新功能也照跑）；
- 找到的 bug：to-issue 定位加工、修复走 bug 修复流程、回归用例入库——本手册只管「找到 + 写出杀它的测试」，不修；
- 性能类问题（慢、耗资源）不在六类里，属基准纪律。
