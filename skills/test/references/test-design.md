# 用例设计与例子

## 从规则选择场景

先写一句可核对的规则，再选择能区分错误实现的输入。以“订单满 100 元减 10 元”为例，99.99、100、100.01 对应临界值两侧与等号边界；随意选三个都大于 100 的金额没有相同区分力。金额单位与精度遵循目标项目契约。

按相关风险选择即可，不要求每次填满矩阵：

| 风险 | 值得验证的差异 |
| --- | --- |
| 分段规则、上下限 | 刚好触发、刚未触发、刚超出；空值是否有不同语义 |
| 状态转换 | 合法前态、禁止前态、重复动作及可观察终态 |
| 错误处理 | 契约规定的拒绝、错误类型、反馈与副作用是否发生 |
| 权限与隔离 | 不同主体对同一资源的结果及未授权操作不生效 |
| 异步与资源 | 取消、晚到结果、重复触发、超时与释放，仅覆盖存在的相关路径 |
| 持久化与装配 | 真实写入后经使用者接口读回，配置或依赖是否实际生效 |

一个测试可包含描述同一行为的多个断言。参数化适合共享同一规则的独立输入；不同前置条件或不同故障原因不能因代码相似就揉成难以定位的大测试。

## 独立期望

有用的期望可以来自明确规格、人工算例、经确认样例、数学性质或独立参考实现。独立参考实现需有自己的可信依据，不能只是把生产算法换个位置复制一遍。

例如约定单价和结果都以整数分表示，期望可直接来自人工算例：

```ts
expect(totalPrice([{ unitPrice: 125, quantity: 4 }])).toBe(500);
```

只把同一乘法和求和循环复制到测试中，并不会增加独立的正确性依据。性质测试也要能排除错误：只有“结果非负”不能证明总价算对，还需按本次规则补具体结果或更强的不变量。

幂等、可逆、输入置换等关系可以构成独立预期。例如业务要求标准化操作幂等，`normalize(normalize(input))` 应与 `normalize(input)` 相等；这不因两侧调用同一函数就失效。但恒定返回值也可能满足幂等，因此还需具体算例约束实际标准化结果。

## 常量与实际消费行为

```ts
expect(DEFAULT_TIMEOUT_MS).toBe(DEFAULT_TIMEOUT_MS);
```

这是恒真断言，没有验证价值。

```ts
expect(DEFAULT_TIMEOUT_MS).toBe(5000);
```

这能发现值变化，但需要解释为何必须是 5000。若数字只抄自声明且没有独立要求，应清理。若要求“请求在 5 秒后超时”，通过受控时钟观察超时边界与错误反馈，更能验证该配置是否实际被消费。

固定协议标识、公开默认值和跨表键一致性有独立契约时可以直接验证。不要为了避免测试常量，删除有效约束或虚构额外生产调用。

## 替身验证了什么

mock 用来控制本次测试之外的依赖，不应替换本次要验证的逻辑：

- 把总价计算函数 mock 成 500，再断言它返回 500，只证明了替身设置。
- 执行真实下单逻辑，断言外部付款接口收到独立算例规定的金额，可以验证外部可观察的请求。
- “空购物车不扣款”可以断言付款接口没有被调用；相邻有效购物车用例应能观察到扣款，使观测不是失效的。
- 调用次数在“不得重复扣款、重复发送、重复写入”这样的契约下有意义；私有辅助函数调用几次通常不属于契约。

单测中的外部替身不能证明真实服务兼容、数据库查询正确或部署装配可用。需要相应证据时复用项目的集成或契约测试；只获准写单测时如实说明边界，不扩展为真实服务接入。

## 回归必须触达真实故障路径

竞态来自多次请求时，单独测试一次请求成功不能锁定竞态；界面未把金额传给计算模块时，单独证明计算模块正确不能覆盖装配缺陷。用例应触达症状发生的调用链，并断言具体症状。

已知 bug 要确认修复前确实因目标症状失败，语法错误、缺依赖或与症状无关的运行超时不是该证据。若目标就是挂起、超时或截止时间错误，受控时钟或有界超时可以构成症状证据，须区分目标缺陷与环境卡顿。给已有正确行为补测试可以直接通过，无需人为制造红灯。
