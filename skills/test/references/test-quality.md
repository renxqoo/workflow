# 质量与清理规则

清理对象由测试的逻辑和契约决定。先看被测调用、输入、期望来源与断言，再判断名称和代码形式。下面列的是问题及处置条件，不是按语法批量删除的规则。

## 保留范围与业务判断

先区分“测试是否有效”与“本次是否长期保留”。一般质量清理不默认排除 UI；用户明确只保留业务回归时，采用以下边界，不机械套用于其他项目或视觉、可访问性专项。

| 测试目标 | 业务回归清理中的判断 |
| --- | --- |
| 金额、资格、权限、状态转换、数据归属、实际读写结果、请求参数及禁止副作用 | 保留能区分错误结果的判断，包括让结果可信的协议、安全与一致性约束 |
| 价格、模型身份、订单状态或发布语言以文本/DOM 呈现 | 核对数据来源、转换与选择规则；文本和 DOM 可以是业务结果的观察入口，不按 matcher 或定位器形式删除 |
| 任意 props 原样显示或复制、标题措辞、图标、加载动画、菜单展开及焦点恢复 | 若只验证通用展示或控件实现，属于可排除目标；“能操作”或“执行了生产组件”本身不足以构成业务保障 |
| UI 操作完成真实查询、创建、付款或恢复流程 | 保留正确对象、金额、权限、参数、持久化结果和副作用；移除无关列数、层级、焦点与提示句要求 |
| 混合用例 | 逐条核对断言。例如保留渠道换算、非法输入不提交与正确重试，删除帮助文案、圆角和按钮动画；按最终目标改名并清理专用装置 |

关注用例实际能拒绝的错误：复制任意传入字符串通常只验证复制控件；从真实发布入口选到正确模型的接入协议、代码或请求参数，可以保护业务结果。接口替身是否合理取决于本次验证边界，不能只凭有 mock、文本或 DOM 判定。

失败原因与保留价值分别裁决。旧文案、定位器漂移、缺少前置数据、上游故障都不能单独决定保留或删除；先确定目标是否在本次范围，再诊断范围内用例的失败。业务退役与本次排除也要分开：排除某项 UI 验收不表示产品已经取消该要求。

| 问题 | 判断依据 | 处置 |
| --- | --- | --- |
| 明确排除的目标 | 用户已经限定长期保留范围，而用例只验证范围外目标 | 删除并注明范围依据，无需为该目标补替代覆盖；混合用例保留范围内判断 |
| 恒真断言 | 同一稳定值与自身比较；无论生产逻辑如何都不会改变结论 | 删除无效断言；若原用例有明确行为目标，补有效断言 |
| 复述声明 | 常量等于声明值，或把静态对象复制一份比较；找不到独立规则 | 删除；若承载真实契约，保留约束或改测实际消费行为 |
| 自建数据自验 | 创建测试对象后检查其属性，未执行任何相关生产逻辑 | 删除；需要验证解析、转换等行为时通过真实入口改写 |
| 自证式期望 | 没有独立约束，只把被测函数的输出当正确答案，或复制算法且没有独立正确性依据 | 改用规格、人工结果、可信样例或有约束力的性质 |
| 只验证替身 | 本次要验证的逻辑被 mock 掉，结论完全来自替身设置 | 恢复真实目标逻辑后改写；无目标行为则删除 |
| 断言过松 | 错金额、错用户、漏结果或重复副作用仍满足当前断言 | 加入能区分目标错误的结果、错误或副作用断言 |
| 名实不符 | 名称声称保护的行为与实际调用或断言不一致 | 先依据需求、消费者和历史回归核实契约；断言有效则改名，名称所述契约有效而断言错误则改断言，未决时保留待查 |
| 内部实现耦合 | 行为相同的重构仍因私有步骤、结构或内部调用顺序失败 | 改为稳定入口上的行为验证 |
| 无独立价值的重复 | 规则、条件、结果和故障探测能力均重合 | 按下文重复项裁决选择保留位置，迁移独有保障后合并或删除副本 |
| 已退役契约 | 当前需求及消费者明确移除该行为，测试只维护旧实现 | 删除相关测试及仅为其存在的测试辅助代码 |
| 测试文件内死代码 | helper、导出等没有调用方或发现路径；遗留注释段已无有效说明用途 | 核对全仓引用、框架发现及动态调用后清理；共享辅助代码和有效契约说明不能仅凭局部无引用删除 |
| 长期停用 | skip 用例长期不执行，停用原因缺失或已过期 | 核实原因和当前契约，恢复执行并验证、确认无价值后删除，或保留有原因和跟踪项的隔离；未决项明确待核实原因 |
| 仅输出观测结果 | 只 log 观测或性能数据，没有可判失败的目标行为、阈值或独立不变量 | 有回归目标则补有效判定，否则按用途保留为采样工具或删除，不计作自动回归保障 |

## 重复项裁决

先比较规则、前置条件、边界、异常、时序和实际故障路径，确认哪些保障重合、哪些独有，再选择承载位置：

- 优先保留断言区分力强、有效场景完整且失败容易定位的版本，不按断言数量排名。不能为合并把不同故障原因揉成一个难定位的大测试。
- 保留真实 bug 的触发条件、关键断言和台账或 issue 引用。可将这些信息迁入保留用例；有引用不等于当前断言仍有效，也不要求保留原文件。
- 装配、信号传递或协议边界的重复候选，优先保留能触达真实 signal/wire 路径的版本。mock 用例若仍保护独立错误路径或边界，就不属于可直接删除的副本。
- 保障等效后，优先放在主题归属明确的文件，沿用项目组织方式，便于后续定位与维护。
- 删除前迁移另一份独有的断言、场景和回归信息，并运行保留用例。独有故障路径无法迁移或证明等效时，继续保留相应用例；记录重复或替换项的覆盖去向；用户明确排除的目标注明范围依据即可。

## 大范围清理

全仓、跨模块或候选多到难以逐项追踪时采用以下流程；局部清理不必建立整仓台账。

1. **固定范围和运行基线。** 记录保留标准、已有修改及候选对应的代码版本；共享文件记录己方变更边界。在目标执行环境核实运行时、PATH、依赖及实际测试命令，先排除命令缺失等环境失败，优先取得绿色基线。分别记录环境阻塞、原有真实失败及偶发失败，不能把它们当作无效用例的证据。无法全绿时，说明可验证范围；范围内保障是否保留无法验证时暂缓相关删除，不要求顺手修复无关缺陷。有覆盖率门禁时同步采集基线及余量。
2. **分区扫描，先列候选。** 按行为主题、目录或共享设施划分范围，记录每区状态和共享依赖，区分已盘点、已裁决和已验证。文件列表、测试名称、关键词命中和覆盖率重叠只用于发现候选，不代表完成语义审查。在可用且获准委派时可并行扫描，统一提供本表、重复项裁决和候选记录要求；扫描结论先列为候选，不能直接作为批量删除指令。
3. **统一裁决并核实。** 先应用保留范围，再跨分区归并重复簇，逐项记录目标行为、范围或契约依据、问题类别、建议处置及待核实项。重复或替换项记录保留位置，明确排除项不要求替代。抽检高风险候选和保留项来校准口径；每个实际删除项仍须有依据，不能以抽检代替。涉及范围、历史回归、共享设施或真实调用链的争议，回到本次要求、实现与契约核实；范围内保障证据不足则保留。
4. **分批修改与验证。** 依据主文件“运行与证据”的批次和门禁要求执行，使失败能定位到具体批次。批量编辑仅消费已经核实的候选，校验文件版本、定位上下文和预期匹配数量，失配时停止重放；修改后检查语法、残留装置与差异。依下文处理覆盖率冲突，不按测试名或正则命中自动删除。
5. **汇总可追溯证据。** 大范围任务将清理报告按项目约定落盘，汇总分区状态、各项处置依据和适用的覆盖去向、实际命令与结果、覆盖率变化、原有失败和未执行项。声明完成的范围必须有对应裁决，不能把盘点或抽检写成全仓审查完成。沿用已有报告位置，不机械创建另一套长期台账。

## 覆盖率冲突

先按项目真实配置区分整体统计、目录聚合和逐文件门禁。可能触及门禁的删除尽早小批复测，不等全部清理后才发现冲突。

- 丢失范围内的业务边界、异常或真实调用链保障时，补有效判断或撤回相关删除；不能以缩小清理目标为由掩盖误删。
- 仅移除用户明确排除的展示/控件覆盖时，不为过门禁补回同类测试。清理授权不等于门禁修改授权：保持配置，报告受影响文件、指标、实际值、阈值及测试通过但门禁失败的状态；未全绿时不宣称项目验证完成。
- 两类损失并存时分别处理。用户要求门禁全绿而又未授权调整冲突配置时，完成可验证的清理与证据后说明剩余冲突，不擅自选取一条要求覆盖另一条。

## 共享改动与隔离验证

已有改动或持续变化的工作区先记录版本与己方文件/补丁边界。对同一文件中的其他改动保留原样；批量编辑和格式化不能把它们吸收为己方变更。

用于证明己方变更的隔离候选应是明确基线加己方补丁。文件混有他人变更时按变更片段重放并检查上下文，不把整份当前文件复制到旧产品基线；匹配失败时重新核对，不能悄悄丢弃对方断言。如验证完整工作快照，明确它包含哪些已有改动，不称为仅验证己方变更。验证前后核对实际输入，报告隔离版本、叠加范围与共享目录的差异。隔离候选通过不代表当前整树通过，持续变化中的一次基线也不代表最终状态。

## 防止误删

- 字面量不等于恒真。`expect(limit).toBe(20)` 可探测值改变，其价值取决于独立契约；不能与 `expect(limit).toBe(limit)` 混为一谈。
- 同一函数出现在断言两侧不自动构成自证。幂等、可逆等性质可以来自独立契约；需判断关系本身能否排除相关错误，并结合具体算例确认完整行为。
- 同一行被不同输入覆盖，不等于测试重复。正常路径、临界值、错误恢复、并发时序和历史回归可能捕获不同缺陷。
- 真实 bug 的回归不会因长期全绿而失效；查证它保护的故障路径及当前契约。
- 外部调用参数、禁止副作用、协议值、错误类型和不变量可以直接断言。精确文案或结构是否重要，也由消费方契约决定。
- 快照可以保护稳定输出。需要确认其中哪些变化有业务意义，避免只因快照大就删除，或未经核对批量更新。
- 新的上层测试存在，不自动证明旧单测可删。先确认旧用例的独立边界和故障风险已被覆盖；不能只看新测试名称或覆盖率。
- 慢、失败、偶发失败可能暴露真实问题。先区分实现缺陷、时序、污染、环境和退役契约；不得通过移除测试掩盖未解决失败。

## 浏览器功能测试清理

- 先应用本次保留范围。在保留交互验收的任务中，视口是触发某条用户路径的前置条件时可以保留，例如窄屏下打开菜单、完成导航或验证焦点约束。固定宽度对应的列数、像素位置或 DOM 层级若没有独立的产品契约，不作为功能测试目标；确有视觉或可访问性要求时，选择能直接验证该要求的方式。
- 失败时先核实页面状态和测试数据：内容是否发布、上游是否故障、用户是否已登录，以及异步结果是否到达。再区分定位器歧义、环境问题和产品缺陷。优先按角色、可访问名称和实际操作定位，并限定查找范围；不要通过增加等待或删除有效断言掩盖问题。
- 退役旧路径的重定向或别名，不自动意味着旧 URL 必须返回 404。新增状态码、跳转目标或不可访问性断言前，须找到独立契约；只确认旧规则已移除时，删除维护旧规则的测试即可。

## 清理证据

每项改写、合并或删除给出简短理由。范围排除项说明用户边界，不谎称原测试无效；重复项指出保留位置；替换项指出对应行为与新入口；退役项指出契约移除依据。小范围可以直接列在交付说明中，不机械创建长期文档或整仓矩阵。

检查删除后仍保留范围内必要场景和错误探测能力，移除仅由已删除测试使用的 fixture、mock 和导入。共享辅助设施先核对其他引用，不扩大到无关生产重构。

运行相关测试及项目要求的门禁，比较实际结果；采集了覆盖率再报告变化。测试通过或行覆盖率不变，都不能单独证明行为保障没有丢失。证据不足时保留该测试并说明待核实原因，不为减少数量强行删除。

统计时区分测试文件、用例声明与参数化后的执行实例；分开报告本轮与累计删除数。测试通过、覆盖率门禁通过、构建通过和完整入口通过分别报告，被前置门禁阻断的后续检查须注明未执行或单独执行的结果。
