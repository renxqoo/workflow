# 数据、事务与跨系统一致性

用于持久化、并发和异步协作设计。数据库与外部系统的实际保证按项目版本核对；以下是判断问题的方式，不是指定技术栈。

## 从访问路径决定数据结构

- 列核心实体、主键与业务唯一性、归属、关联、生命周期及数据保留。字段说明单位、来源及能否改变。
- 把可由数据库保证的不变量落实为适当的唯一、非空、检查或引用约束，确认目标引擎支持及既有数据能否满足。应用验证提供反馈，不替代并发下的约束。
- 按实际过滤、排序、关联及写入成本提出索引；说明支持哪个查询。表规模与查询计划未知时，将收益写成待验证假设。
- 价格、规则版本等需要历史稳定性的业务事实考虑快照或版本引用；不能让历史记录随当前配置静默改变。
- 缓存、搜索及分析数据明确来源、延迟容忍、失效与重建，不能与权威写入形成未定义的双向同步。

## 写清本地原子边界

逐步列出读取什么、检查什么、锁定或按什么版本更新、写入什么、何时提交、提交后做什么。针对不变量选择现有隔离级别、条件更新、唯一约束或必要锁，不凭“用了事务”声称并发正确。

以竞争路径核对：两个创建同时查无记录、两个请求扣同一余额、取消与完成同时更新、超时客户端重试。说明冲突怎样被发现，是否重试，以及重试何时终止。锁顺序和长事务只在实际涉及资源竞争时展开。

不要在未分析的长事务里等待远端调用；数据库回滚不能撤销已发出的外部副作用。连接中断或超时可能意味着结果未知，恢复应能凭稳定标识查询状态，而非直接认定失败再创建一次。

## 跨系统动作

| 失败窗口 | 设计必须解释 |
| --- | --- |
| 数据提交后，通知还没发出进程就退出 | 是否要求可靠送达，谁记录待发工作并恢复，还是业务允许丢失 |
| 外部成功，但本地没记下结果 | 如何用同一尝试标识查询或安全重试，避免重复收费等副作用 |
| 消费者执行完成但确认丢失 | 重投后怎样识别已处理，以及去重与业务提交怎样关联 |
| 事件乱序或同一业务事实多次通知 | 如何依据状态、版本或权威查询收敛，而非仅按到达顺序覆盖 |
| 补偿调用失败或结果未知 | 如何持久保留待处理状态、重试预算与人工处理入口 |

本地业务提交与可靠派发确实需要绑定时，可评估现有任务表或 outbox；收到事件的去重可用现有 inbox 或业务唯一键。必须说明记录与业务变更的原子关系，以及派发的抢占、确认、超时恢复和重复处理。模式名称本身不是保证，也不是每条通知的必需组件。

补偿是一项新的业务动作，其权限、幂等和失败恢复须设计；它不是对远端事务的自动回滚。无法给出跨系统保证时，明确最终一致性、中间态、对账和人工介入条件；业务不接受这些结果时重新选择边界或机制。

## 终态与晚到事实

将内部状态转换与外部支付、退款、配送等事实分开记录。晚到成功不能无条件复活已取消业务；也不能因为业务已终止就丢弃真实扣款。按已确认业务规则选择退款、补偿、对账或人工处理，并保证恢复任务不会因进程退出丢失。

推演时给出“前态 → 竞争/失败 → 最终状态及副作用”，同时注明依赖的机制。尚未运行的推演是设计依据，不是实测证据。
