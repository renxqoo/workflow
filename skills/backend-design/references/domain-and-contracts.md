# 领域、状态与接口契约

用于业务建模、API 或事件契约设计。以本次动作和实际消费者为范围，不按模板补全所有实体与接口。

## 不变量与状态

- 用可观察规则表达正确性，例如“同一租户的同一创建意图只产生一份订单”“取消成功的订单不会继续履约”。具体业务规则由需求确定，不能把示例当成通用约定。
- 标明实体或聚合、生命周期、权威写入者及关联标识。金额、单位、时区和精度显式表达，客户端输入不能替代服务端可信价格或归属判断。
- 状态转换写前态、事件、条件、后态与副作用；对重复、并发和迟到事件规定结果。业务终态不意味着外部事实停止变化，必要时用支付、退款或对账记录表达后续事实。
- 用户或租户身份从已认证上下文取得，资源查询与修改必须受其归属约束。请求体里的 tenant_id、owner_id 或资源 ID 不是访问许可。
- 只在术语确有歧义时补领域词汇。数据表名不自动等于业务概念，领域说明也不承担全部存储细节。

## 接口应让调用方知道什么

1. 谁可以调用、作用于什么资源、前置状态是什么。
2. 输入格式、必需信息、边界和字段来源；哪些信息由服务端计算。
3. 返回的是已完成结果、已受理任务还是当前状态，以及如何查询最终结果。
4. 业务冲突、无权限、非法输入、依赖失败和未知结果如何表达；重试是否安全。
5. 版本与兼容约束；分页顺序、过滤和游标的稳定性只在实际需要时设计。

选择 HTTP、RPC、事件或内部接口应服从现有消费者。沿用项目状态码与错误协议；新建议给出明确映射，不把示例码当现有约定。事件注明产生时机、实体版本及消费者可依赖的事实，避免泄漏随意变化的内部表结构。

## 幂等与访问隔离

对需要安全重试的写入，说明幂等键的作用域、载荷等价规则、保留期限和并发请求行为。相同键相同意图返回相同操作标识或可追踪结果；相同键不同意图应有冲突语义，不能静默重用另一个请求的结果。

去重结果持久化与业务写入如何共同完成须有机制。只在内存记住请求或先查后写都不足以说明跨实例、进程退出与并发时的保证。跨租户不能共享不带归属的去重记录。

区分客户端业务请求键、外部调用尝试键、供应商事件 ID 和业务实体 ID；它们解决的重复来源不同。重复事件也可能使用不同事件 ID，需核对业务转换和副作用是否还能重复发生。

外部回调验签只证明来源；更新业务前还要核对商户/租户、已保存的尝试与资源映射，以及相关金额、币种和结果语义。不能仅凭回调里的订单 ID 更新任意资源。

幂等结果重放仍须完成当前授权与归属校验，不能通过知道一个请求键读取别人的响应。只读操作或无需重试的本地动作不机械增加幂等存储。

## 交接接口设计

对关键接口给一个成功示例及相关的冲突/重试示例，列出仍未确认的外部保证。调用方应能知道下一步做什么，实施方应能知道哪些不变量由哪一层保证。
