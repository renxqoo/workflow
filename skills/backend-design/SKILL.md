# 服务端设计

把服务端业务需求转成能实现、能恢复、能验收的契约。以业务不变量和数据归属组织设计，再确定 API、持久化、事务及跨系统协作；技术组件应服务于具体要求。

## 1. 确定业务与已有约束

- 读取目标仓库 AGENTS、相关服务入口、调用方、数据模型、迁移、测试和已有设计。确认当前行为、目标行为、既定技术栈及外部契约；缺少实现时以明确需求设计，不编造现有能力。
- 提取目标用户、关键业务动作、状态、数据敏感性、访问隔离与质量要求。吞吐、延迟、数据量和可用性注明依据；未知值不转成容量承诺。
- 复用已经接受的系统边界和方案。只有职责或数据归属确实冲突时才指出架构问题，不因设计一个接口重开全系统选型。
- 只澄清会改变契约、数据所有权、重要业务规则或验收的缺口；非阻塞项标明假设并继续。不为每个字段或技术细节要求确认。

默认交付方案；不自动修改产品、执行 DDL/迁移、接入真实支付或其他外部服务。文档写入沿用本次要求与项目位置；只讨论时在回复中交付。已有明确实现授权时，完成必要设计后按项目开发流程实施。

## 2. 先写不变量、状态与契约

按 [领域与接口契约](references/domain-and-contracts.md)，从业务动作写出独立于实现的正确性要求：谁能做、在什么状态做、哪些结果必须一起发生、哪些操作可以重试或取消。

明确权威状态、允许的状态转换、触发者与竞争条件。跨系统动作区分业务状态和外部事实，避免一个含糊的 success 字段同时表示受理、持久化和处理成功。

按实际消费者选择接口形式，给关键请求、响应、错误及重试示例；认证身份、资源归属、兼容性和幂等语义落到契约。小型只读接口只处理相关读写与隔离要求，不强加消息、状态机或幂等键。

## 3. 把契约落实到数据与一致性

按 [数据与一致性](references/data-and-consistency.md) 明确核心数据、键、约束、访问路径及索引依据。区分领域规则、数据库约束、事务边界、并发控制和外部协作，不用“加事务”代替具体设计。

对相关失败窗口走一遍读写和外部动作的先后：重复请求、并发更新、提交后进程退出、调用结果未知、重复或乱序事件。说明怎样发现、去重、重试、补偿或对账，谁持有最终责任。

跨数据库与外部服务的操作不假设共享本地事务；也不默认引入分布式事务、事件溯源或消息队列。已有组件按实际保证使用，新能力须说明解决什么已知缺口及代价。

## 4. 补齐运行与演进

相关路径参考 [运行与演进](references/operations-and-evolution.md)：超时预算、重试上限、背压、任务恢复、缓存一致性、可观测性与数据变更。日常读接口不必展开全部内容。

容量和性能选择与实际查询、工作负载及部署条件关联；不能用缓存掩盖错误数据归属，不能把重试当成所有失败的恢复方式。涉及外部契约或存量数据时列兼容顺序、回填及回退限制。

## 5. 场景核对与交付

用关键成功路径和足以挑战设计的失败场景核对不变量，参考 [方案与验收格式](references/design-output.md)。每个场景说明前置状态、动作或交错、期望结果、保证机制和验证入口；状态表或伪代码推演注明未实跑。

优先复用现有测试、集成或进程入口；确有不确定性时可用隔离探针验证，不为一份方案新建完整服务。数据库方言、隔离级别、框架及外部 API 的具体保证应核对目标版本的配置和权威资料，无法核实则记录待验证条件。

交付足够实施的领域/状态、接口、数据与事务说明，以及适用的恢复、演进和验收。说明关键取舍、假设、未决项和实际验证限制。按规模合并为一份方案，不要求每个任务生成完整 API 文件、DDL、ADR 和多张图。

## 与相邻技能的边界

- `architecture-design` 负责系统整体职责、部署和关键架构选择；本技能细化服务端契约，不重新推翻已确认决定。
- `feature-dev` 实施已授权的方案；`repo-migration` 处理明确的架构或数据迁移实施。设计请求不自动变成实施任务。
- `code-review` 审查现有实现；`test` 与 `verify-harness` 按需要提供测试或系统性验证方法。本技能自足，缺少相邻技能时继续完成可做的设计。
