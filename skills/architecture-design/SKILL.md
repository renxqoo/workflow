# 系统与模块架构设计

把业务目标和实际约束转成清楚的职责、接口、数据归属与协作方式。设计深度随决策风险变化；调用方应能通过接口完成业务动作，无需掌握内部表示和执行顺序。

## 1. 固定问题与设计范围

- 区分新系统设计、已有架构调整和方案评估。读取适用的 AGENTS、相关实现、调用方、配置、测试和已有设计记录；已有有效决定直接复用，不因启动技能重新选型。
- 从用户目标提取关键业务路径及约束：谁使用、处理什么数据、外部依赖、部署与运维条件。规模、延迟、可用性和一致性要求注明来源；未知数字保留为假设或待测项。
- 用户已选定技术栈或架构目标时，在该约束内设计。发现矛盾要给出影响及可行替代，不能静默改成自己偏好的架构。
- 仅当缺失选择会改变范围、契约或重要取舍且无法调查时询问；继续完成不受影响的设计。小问题可以只给接口与职责建议，不强制完整架构报告。

设计或评估请求默认交付方案，不修改产品代码、数据库、部署配置或外部系统。保存设计按用户要求和项目约定；只要求讨论时直接在回复中交付。已明确授权实现时，可在完成必要设计后继续既有实现流程，不增加形式审批。

## 2. 从业务路径划分职责

沿一条核心路径明确入口、业务决策、状态所有者、依赖及结果，再补与本次目标相关的错误与恢复路径。区分当前结构和建议结构。

按 [边界与方案比较](references/boundaries-and-options.md) 识别共同变化的知识与规则，把它们集中到能维护不变量的模块。说明每份权威状态由谁写、其他模块如何读取或请求改变；派生副本也要有更新与失效责任。

先写真实调用示例或交互，再确定接口。接口应包括输入输出、错误、时序及副作用约束，不能只列类名或分层目录。模块边界、部署边界和团队边界分别说明，不把一个模块自动变成一个服务。

## 3. 比较影响结果的选择

对存在真实取舍的关键决定提出结构不同的可行方案，按业务约束比较数据归属、调用成本、故障传播、变更范围、运维与演进成本。已有清楚结论或局部调整不凑候选数量。

说明推荐方案、舍弃理由及什么新证据会改变决定。微服务、消息系统、缓存和通用扩展点应对应具体需求或瓶颈；项目已明确采用的能力则评估其实际用法，不擅自移除。

接口行为或性能存在可实验的不确定性时，按 [设计验证](references/validation.md) 选择便宜的隔离探针或原型。只验证关键假设，不先搭完整系统；未经运行的推演标明静态判断。

可独立比较的复杂方案可使用当前宿主的委派能力，默认继承模型并使用新上下文，提供目标、约束、材料位置和输出范围。候选产物分开保存，主会话核对依据；没有委派能力时直接比较，不把多方同意当作证明。

## 4. 闭合关键流程与演进

对影响本次目标的同步调用、异步通知、超时、重试、取消、部分失败及恢复，明确责任和可观察结果。跨存储或外部系统的动作不能仅靠图中的一条箭头假定为原子操作。

已有系统的结构变化列出受影响调用方、契约、状态与发布顺序；确有过渡期时说明兼容策略、退出条件及回退限制。目标是迁移实施时才采用迁移流程，不把设计建议自动变成改造任务。

## 5. 交付可实施的设计

参考 [设计交付格式](references/design-output.md)，按规模选择必要内容：目标与约束、模块及数据归属、调用示例与关键流程、方案取舍、演进顺序、验证方式和未决项。图能帮助理解边界或协作时使用当前可用格式。

关键结论引用实际材料，区分事实、建议、假设和已验证结果。重要且难逆的取舍沿用项目 ADR 记录；不为每个实现选择新建文档。实现方应能据此知道改什么、保留什么、怎样判断完成。

## 与相邻技能的边界

- `backend-design`：需要细化服务端领域、API、数据、事务与异步恢复时参考；已有架构决定作为输入，不重开相同讨论。
- `feature-dev`：实施已授权的设计；普通局部实现仍沿用其轻量方案，不因跨一个函数就启动架构设计。
- `repo-migration`：按已确认目标实施迁移；`code-review` 负责代码正确性与具体风险审查。
- `how` 与 `why` 分别解释现状和调查历史缘由。本技能自行取得必要证据，不强制调用其他技能或要求先安装它们。
