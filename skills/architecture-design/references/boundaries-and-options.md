# 边界与关键方案

用于系统划分、职责调整、依赖重组或架构选型。围绕本次业务路径比较，不把所有条目变成必填清单。

## 用所有权解释边界

- 先列业务动作及必须共同保持的规则，再决定模块。一次变化总要修改多处时，查找是否将同一知识拆散，而非直接增加协调层。
- 对关键状态注明权威来源、写入入口、允许的转换和读取方式。缓存、搜索索引、报表等派生表示说明延迟、重建与失败恢复。
- 接口应让调用者完成一个有意义的动作。若调用方必须按顺序调用多个内部步骤才能保证正确性，检查协调责任是否放错位置。
- 分离外部协议、框架对象与内部业务表示的变化；确有适配责任时保留边界。不要仅为了让测试替换一个函数而暴露整个内部结构。
- 区分依赖调用与数据共享。两个模块共用数据库并不意味着可以任意写对方表；分成两个进程也不能消除共享数据上的竞争。

深度由接口隐藏的规则与协调成本体现，不能按实现行数衡量。小接口也可能泄露复杂的顺序、配置或生命周期要求。

## 方案比较的依据

| 选择 | 应查明什么 |
| --- | --- |
| 模块化单体或独立服务 | 是否需要独立部署、隔离、扩缩容或团队所有权；代价是否包含协议、网络失败、数据一致性和运行维护 |
| 同步或异步协作 | 用户何时需要结果，允许何种延迟，调用方如何得知最终成功或失败，事件重复和乱序由谁处理 |
| 共享库或服务接口 | 是共同的稳定规则，还是独立变化的业务；版本耦合、可用性耦合与测试成本分别如何 |
| 原地调整或过渡迁移 | 消费者能否同时切换，持久化数据能否转换，是否存在不可逆写入，过渡期怎样结束 |

候选可以在状态归属、模块组合或通信方式上不同，不应只是同一结构换三种框架名称。比较相同的业务情境，区分一次性改造成本与长期维护成本。容量或成本数字没有依据时写待测，不用打分表掩盖未知。

## 沿实际调用识别设计成本

- 多个模块重复解释同一状态、协议字段或业务规则，修改必须同步时，明确唯一解释者。
- 传递层只转发参数时，判断它是否增加必要的适配、访问控制或生命周期责任。没有实际责任再考虑合并。
- 依赖循环先追踪哪个知识或所有权放错位置；事件、接口或依赖注入并不自动消除语义循环。
- 拆服务后若仍需跨库同步提交，说明真正的一致性要求及能满足它的路径。业务不接受中间态时，不能用最终一致性替代目标。
- 对扩展点说明当前变化来源与调用者。已明确的未来契约可以作为约束，臆测的扩展需求不作为增加层次的依据。

## 记录取舍

写明问题、已知约束、选择、实际备选、后果及重新评估条件。ADR 沿用项目格式与编号，仅用于值得长期保留的决定。建议结构不冒充已落地结构；已接受决定的修改要说明新的依据。
