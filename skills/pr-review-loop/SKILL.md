# PR 审查循环（建 PR → 组路 → 审查-修复-复查循环 → 收口）

本 skill 沉淀自多次「代码写完 → PR 建立 → 多 agent 对抗审查 → 循环修复复查 →
安全合并」实战。核心信念：

**门禁防「不过」，对抗审查防「过了但错」——写代码的会话有自证偏差，
独立上下文 + 明确被指示「假设代码是错的」才能抓到规格盲区；
多路独立同报同一问题 = 最高置信信号；
审查是手段不是仪式——空审查是合法产出，为凑数制造的 finding 是污染；
每条 finding 必须处置，不存在「看过没动」。**

## 阶段 0：入口与环境探测（进入即做，不问用户）

**入口形态三选一：**

1. PR 已存在 → 取 PR diff，直接进阶段 2；
2. 代码已写完、验证命令已绿、无 PR → 走阶段 1 建 PR；
3. 代码还没写完 → 退出本 skill，告知用户这属于实现类 skill 的范围。

**环境能力探测（决定执行形态，缺什么降级什么，如实标注）：**

- **基准分支**：`git symbolic-ref refs/remotes/origin/HEAD`（取不到时
  `git remote show origin` 或看远端仓库设置；main / master / develop 均常见）；
- **验证命令集**：枚举 CI 配置（`.github/workflows` 等）里**每个 job**，
  逐个映射出本地等价命令；再读 `package.json` scripts / `Makefile` 补齐。
  typecheck / lint / test / build 只是最小集——format / coverage / 边界
  检查等任何 CI 强制项都进验证命令集。不要发明命令，用项目已有的；
- **环境对齐**：读 CI job 的 services/env 块（数据库、Redis、密钥），
  本地缺的依赖会让部分测试静默 skip（看起来绿，CI 必挂）——本地跑不了
  的项在收口报告标注「本地未覆盖、CI 将验证」，不当全绿报；
- **PR 工具**：有 `gh` CLI → 建 PR；无 → 推分支，报告 diff 供人工审（审查循环
  照常跑，只是产物是「分支 + 报告」而非 PR）；
- **子 agent 工具**：有 → 并行多路审查（本 skill 完整形态）；无 → 降级为
  单会话串行自审（自证偏差没有被隔离），降级形态写进收口报告的
  环境降级声明节；
- **会话恢复能力**：平台能向已 spawned 的 agent 续发消息（resume）→ 用
  「原者复查」机制；只能一次性 spawn → 每轮 fresh agent + 复查消息里
  重放其上轮报告的关键 finding（上下文重建，成本略高）。

## 阶段 1：建 PR（仅当 PR 不存在）

1. **先门禁后人工**：跑完整验证命令集，全绿才继续——门禁便宜（机器跑），
   审查贵（独立上下文），别让审查者发现 lint 就能抓的问题；
2. 从基准分支切 feature 分支（已有则复用）；提交遵循目标仓库的提交纪律
   （无既有纪律时用 Conventional Commits）。git add 逐路径点名——目的
   是避免夹带未审文件进提交，而不是仪式；
3. 推远端，建 PR。PR 描述含：改动摘要、验证结果（具体数字）、已知风险。
   没有 gh CLI 的仓库退化为「推分支 + 报告」。

## 阶段 2：组审查路（按 diff 风险面，路数由 agent 按风险面裁量）

组路数量是判断题不是固定配置：路 A（正确性）恒定；风险路按命中组。
权衡的两端——多一路多一份独立信号（多路独立同报 = 高置信），但审查
预算有限且独立信号边际递减（第 N 路的发现大概率已被前面覆盖），并发
agent 数也受平台限制。经验缺省：中等风险 diff 组 2 路（路 A + 最重的
一个风险面），高风险/多面 diff 加到 3；更低或更高由你按 diff 实际
风险面定，并往组路记录里写一句为什么。

通读 diff + commit message，识别风险面后组路：

- **路 A 恒定——正确性/契约**（任何 diff 都适用）：读
  `references/rubric-correctness.md` 作为章程；
- **路 B（+C）按触发条件**：读 `references/rubric-risk-lanes.md` 的实质性
  过滤段 + 判定表，命中哪条组哪路（UI 前端 / 并发事务 / 契约影响 /
  安全敏感 / 生产可用性 / 性能量级）。都没命中 → 路 B 缺省为「结构完整性与
  可维护性」底线章程（也在该文件内）；
- **各路指令刻意不重叠——物理上不重叠**：每路只喂它自己的章程节
  （同文件不同节也只给节锚点，不给全文），否则多路同报会被当成
  「多路共识」高置信信号——章程重叠制造的共识是伪共识，污染置信信号；
  同一问题被多路独立发现 = 高置信，处置优先级置顶。

派发用 `references/reviewer-prompt.md` 模板填：意图（commit message / PR 描述
提炼）、仓库/分支/基准（绝对路径；模板内含 diff 获取与空 diff 降级链，
不贴全量 diff 进 prompt）、对应章程的**文件绝对路径 + 节名**（喂节不喂
全文）。**审查 agent 只读**——明确禁止其改代码，代码修改永远回到主会话。

## 阶段 3：审查-修复-复查循环（最多 5 轮，软上限）

每轮流程：

1. **收报告 → 汇总去重**：多路同报的置顶（最高置信）；单路 finding 按严重级
   排序（blocker > major > minor > nit）；
2. **逐条强制归入四分类**（读 `references/lead-judgment.md` 的判断框架）：
   - **修**：blocker / major，改代码（优先让该类错误写不出来的修法）；
   - **顺手修**：低成本 nit 且不扩大 diff（改动半径几行内）；
   - **落档不改**：有明确理由不改，理由写进复查消息让审查者确认；
   - **驳回**：引用 lead-judgment 的过滤原则显式点名（hypothetical vs. actual /
     premature abstraction / 换我不会这么写 / missing context / nitpick gravity），
     多路共识的 finding 驳回时必须给比单路更强的证据；
3. **有代码改动** → 重跑验证命令集全绿 → 逐路径提交 → push（复查看的是远端
   最新 diff，不 push 不发复查）；**零改动轮（全落档/全驳回）同样发复查**
   （HASH 填当前 HEAD）——该路需要显式「通过」才能结清；
4. **发复查消息**（`references/recheck-template.md` 模板）：给**原**审查 agent
   （上下文连续，不换新 agent），带 commit hash + 已修清单 + 落档不改项及理由，
   **只问「通过 / 不通过 + 理由」**——不许展开新审查面（防范围膨胀）；
5. 「不通过」→ 回到 1；「通过」→ 该路结清。

**退出循环（任一满足）：**

- ✅ 所有活跃路「通过」+ 验证命令绿 → 阶段 4 收口；
- ⚠️ **5 软轮上限**仍有 blocker/major 未清零 → 不直接放弃，先做诊断三分类
  再停下报告用户：
  - **修复引回归型**（每轮修 A 坏 B）→ 实现有系统性问题，建议回炉方案
    而非继续打补丁；
  - **审查标准漂移型**（每轮换角度提新 nit）→ 换审查指令或收窄范围，
    不是迁就无限审查；
  - **真实复杂型**（问题确实难，逐轮在收敛）→ 如实报告进度，用户决定
    是否继续烧轮次；
- 🚨 连续 2 轮零新发现零改动（审查空转；容忍 2 轮而不是 1 轮，是因为
  单轮沉默可能只是审查者状态波动）→ 判定收敛，剩余项交用户裁决。

## 阶段 4：收口判定（「可安全合并」的完整条件）

全部满足才算完（缺一即不算）：

- [ ] 所有审查路返回「通过」；
- [ ] 验证命令集全绿，且是修复后的**最终代码**跑的（不是修复前的缓存结果；
  带构建缓存的仓库用缓存旁路重跑受影响部分（构建工具的强制重跑
  选项）——或核对输出确为 cache miss）；
- [ ] 每条 finding 已归档处置（修 / 落档 / 驳回），无悬空项；
- [ ] 「落档不改」与「驳回」的理由在复查中获审查者确认（或审查者未反对）；
- [ ] **防假绿抽查**：对 diff 逐 hunk 检查——新增 skip / 被注释的用例 /
  被删或被改的断言，与基准分支比**增量**（仓库既有的条件跳过模式不计）；
  验真产物本身，不验「它说它过了」；
- [ ] 处置台账已回写 PR 描述（审查记录节），本地未覆盖、待 CI 验证的项
  一并列出。

产出收口报告（固定骨架，字段不漂移）：

```
# 收口报告：<PR 标题/分支名>
## 结论：可合并 / 不可合并（原因）
## 循环：N 轮；各路状态（路 A：通过第 X 轮；UI 路：通过第 Y 轮…）
## 处置分布：修 X / 顺手修 N / 落档 Y（已确认 Z）/ 驳回 M（理由见台账）
## 验证数字：<逐命令的具体数字，含环境降级项>
## 本地未覆盖、待 CI 验证：<清单或无>
## 已知残留：nit 级清单或无
## 环境降级声明：本次运行的降级形态（无 gh / 无子 agent / 单路串行等）
```

**合并与部署由用户决定，本 skill 不自动合并。**

## 全局纪律

- **角色分离是机制不是建议**：审查者只读，实现者不审查自己；
- 修复必须 push 后才发复查（有代码改动时；零改动轮见阶段 3 第 3 条）；
  复查尽量找同一个 agent（会话恢复不可用时按阶段 0 降级形态重建上下文）；
- 每轮先门禁后审查；审查指令里「空审查是合法产出」（no findings and stop）
  ——防为凑数造 finding，这是不过度执行的第一道闸；
- minor 的准入门槛：必须指出具体的将来成本，答不出将来成本自动降 nit
  （防品味倾倒）；
- 用户可随时打断；每轮结束简报状态（第几轮、还剩几条未清零）；
- 复查消息短（只带增量，不重贴 rubric——审查者的注意力也是预算）。
