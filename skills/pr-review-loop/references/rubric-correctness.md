# 路 A 章程：正确性 / 契约（恒定路，任何 diff 适用）

你是带着「这段代码是错的」的假设来审的。

**先找承重事实**：这个 diff 的安全性大概率系于**一个**事实
（如「这个调用只删已失效的缓存条目，无其他副作用」）。找到它，
把证据推到你能达到的最高级，其余维度按下面的清单过——时间花在
承重事实上，不在一张可能清单上均匀浅扫。

以下五个维度是信号清单。不是每个维度都适用每段 diff——用判断力，
不硬凑。每条 finding 必须给出证据（执行路径 / 调用链 / 实测），
纸面断言不算。

## 1. 正确性

代码真的做到了意图所说的吗？

- 边界：空输入、nil/undefined、边界值、并发访问；
- 错误处理：错误被捕获、传播还是静默吞掉？happy path 和 sad path 都成立吗；
- 经典错型：off-by-one、类型强转、整数溢出、字符串编码、时区；
- 状态管理：竞态、stale closure、悬空引用；
- 幂等：这个操作跑两次会怎样？上次跑一半崩了，重跑会怎样？
  答案如果是「取决于留下了什么状态」，就缺一个对账/清理步骤；
- 并发：多个执行体能碰同一份可变状态（文件/分支/共享数据）时，
  访问是结构性串行化（锁/阶段/独占所有权），还是靠约定——约定撑不住；
- **被风险路过滤掉的面的附带检查**（详见 rubric-risk-lanes 实质性过滤节）：
  硬编码常量值本身的正确性（URL 拼写/域名/版本号/魔法数字）；样式类
  改动的继承链影响（替换式覆盖丢掉颜色/填充继承类）；单行文案的
  正确性与语法；内部导出行为语义的变更（错误码映射、返回值含义）。

发现疑似 bug 时追踪执行路径。不要只标「这里可能是 null」——展示让调用链
走到 null 的那条路径。

## 2. 根因 vs 症状

代码修的是真问题，还是在给症状打补丁？这通常要看改动文件之外——读调用方、
被调方、类型定义、兄弟模块（用 Read / Grep / Glob 自由探索），理解改动
所在的架构再判断层次对不对。

- 掩盖更深不变量违反的 guard 分支；
- 掩盖破裂契约的重试逻辑；
- 把建模错误静音的类型断言；
- 看到 workaround 就问：为什么需要它？正确修法长什么样？
- 修在模块 A、实则该修模块 B 契约的；
- 用注释/约定说「别这么干」的地方，问一句：能不能改成类型约束、lint 规则
  或运行时检查，让错误做法根本写不出来。

## 3. 意图对齐

代码 vs 声明的意图（commit message / PR 描述）。审执行，不审意图本身——
假设目标是正确的，挑战实现。

- 代码做了意图之外的事（隐藏职责）；
- 意图承诺了但代码没做（半成品）；
- 「不处理」的边界没写清归属——没写清的不处理迟早变成隐藏职责。

## 4. 验证完备

从读代码能看出它 work 吗？

- 有测试吗？测的是行为还是实现细节？
- 有能在回归时拦住的断言/不变量吗？
- bug 修复：有针对该 bug 的回归用例吗（在旧实现上会失败的）？
- 碰了集成边界：全路径测了吗？
- 查真东西不查代理：验活用文件 mtime 或缓存而不是读真值，是验证缺口。

## 5. 仓库契约

每个仓库有自己的机器锁定契约，agent 自己去发现（不要假设，去 grep）：

- 架构测试（`architecture.test.ts` / `**/arch/**` / `layer` 关键字）——
  导入白名单、分层边界、文件集合快照；
- i18n parity 测试（en/zh key 树全等之类）——新增文案键双侧同步了吗；
- 词表封闭性（枚举 == 文档词表）、导出面测试、快照测试；
- `CODEOWNERS`、ADR 目录、`CONTRIBUTING` 里的本地规约。

diff 违反了任何一条机器契约 = 直接 blocker，不用犹豫。

## 证据等级（每条关键 finding 自标停在哪级）

1. 我说的（自身无价值）；
2. 指到了行（真实 file:line）；
3. 展示了坏情况到不了/到得了（逐步走失败路径）；
4. 跑了（脚本/测试调真实代码，错了会响）；
5. 在运行中的应用里复现。

对库函数行为、类型系统行为、合并语义这类断言，环境允许时**要到第 4 级**
（写个脚本实际跑，错了会响）——「我记得 twMerge 是这样合并的」不算证据。
只读沙箱跑不了代码时，声明降级到第 3 级并把「未能实际运行」写进
finding 的证据级标注——降级是诚实，不降级地装跑是造假。
