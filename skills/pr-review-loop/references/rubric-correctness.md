# 正确性与契约章程

先核实支撑改动正确性的关键事实，例如输入是否已校验、删除是否仍被引用、状态转换是否保守恒。只检查与本次改动有关的维度，不为清单凑发现。

## 正确性

- 用户可观察的成功、失败和取消路径是否符合目标契约？
- 边界输入、数值/编码/时区、空态和重复操作是否有具体坏路径？
- 状态更新、订阅和异步响应是否可能乱序、悬空或遗失清理？
- 共享可变资源有实际竞争时，指出执行交错和后果。
- 常量、URL、单行文案和样式小改动也按实际影响核实，但无需额外组路。

追输入和调用方，不以“可能为空”代替可达条件。编译期能阻止的误用与真实不可信输入分开判断。

## 根因与范围

查看相关调用方、被调用方、类型定义和测试，判断修改是否消除已证实根因。类型断言、重试、guard 或新抽象本身不是缺陷；需要说明其掩盖了什么具体错误。不为未来假设需求要求重构，不擅自扩大任务。

## 目标对齐

本次用户要求、已确认业务规则和明确契约定义目标；当前代码/测试用于核实现状。说明未实现的承诺、未授权的新行为或目标歧义，不能用现有缺陷否定新需求，也不能由审查者悄悄改目标。

## 验证质量

测试应验证外部行为、边界、不变量和错误路径；期望值来自独立依据。只复述声明、测试自己构造的数据或绑定私有调用顺序不能证明目标正确。

bug 回归应能因该缺陷失败；契约测试起初通过并非无效。结合已有单测、集成和真实产物验证寻找缺口，避免要求每个边界都上 e2e。环境未覆盖的链路明确说明，不自动补新框架。

## 仓库约束

从 AGENTS、实际脚本、配置和 CI 找到适用的架构/导入边界、公开导出、国际化、格式、owner 和覆盖率要求。违反仍适用的约束是具体风险；若本次目标明确调整该约束，核对实现、调用方、门禁和文档是否一起迁移，不将旧快照视为不可更改的规格。

## 证据

区分：静态位置、已追踪失败路径、实际命令结果、运行应用复现。关键第三方行为在权限和成本允许时用真实检查验证，不以记忆当证据。不能运行则说明静态推断与限制，不能伪称实测。

每条有效发现写触发条件、位置、后果和证据；空审查可以明确无发现。最终结论只对应被审范围和准确版本。
