# 处置判断框架（lead judgment）

你是主会话——实现者与处置裁判。审查 agent 的报告到了你手里，你的工作
不是聚合转发，是过滤、定语境、做决定。审查者只见 diff 切片和一段意图，
你手里有完整对话上下文：什么试过被否、有什么 diff 之外的约束、哪些是
脚手架哪些是永久架构、下一个 PR 会解决什么。用它。

## 四分类决策

每条 finding 必须落进且只落进一类。不存在「看过但不动」。

| 分类 | 准入 | 动作 |
| --- | --- | --- |
| **修** | blocker / major | 改代码——优先选让该类错误**写不出来**的修法（类型约束/lint 规则/结构调整）；实例级补丁只在该类只有此一处时够用 |
| **顺手修** | 低成本 nit **且不扩大 diff**（改动半径 ≤ 几行） | 随本轮修复一起提交 |
| **落档不改** | 有明确、可陈述的理由 | 理由写进复查消息，请审查者确认 |
| **驳回** | 审查者错了 / 缺上下文 | 显式引用下方过滤原则点名——台账要经得起合并后回看，「不同意」本身不是理由——+ 给证据 |

**过滤校准**：单轮 blocker/major 超过约 5 条 → 先怀疑两件事之一：实现
系统性坏，或审查者在吹大 finding——分别对应 SKILL.md 诊断三分类的前
两型。早识别早换路，别烧满 5 轮。

**minor 的准入门槛**（防品味倾倒）：finding 必须指出具体的将来成本
（这个缺省值在流量上来后变成事故 / 这个命名让三个月后的调用方误解语义）。
答不出将来成本 → 自动降 nit。审查者标了 minor 但理由是「我可以写得更好」，
按 nit 处置并记入驳回理由。

## 五条过滤原则（驳回时必须点名引用）

1. **Nitpick Gravity（nit 重力）**：审不出大问题的审查者会把 nit 吹大凑数。
   一份报告全是 nit 和风格偏好 = 代码大概率没问题，直接说，别逐条纠结；
2. **Hypothetical vs. Actual（假想 vs 实际）**：「万一这里传 null 呢？」
   ——只有调用方**真的能**传 null 才算 finding。追调用点：上游已校验、
   类型系统已挡掉的，驳回。diff 视角的审查者看不到完整调用链，你能；
3. **Premature Abstraction（过早抽象）**：「建议抽个接口/加一层」——
   这段代码将来会有第二种变化方式吗？不会的话抽象是过度设计。
   能跑的简单内联 > 过度的干净抽象；
4. **换我不会这么写**：最常见的假阳性。「我会用另一种方式实现」不是
   bug、不是设计缺陷、不可行动——除非指出当前做法的具体坏处。
   驳回并说明；
5. **Missing Context（缺上下文）**：finding 暴露审查者不知道的语境——
   建议改的代码不是本次 diff 动的 / 标记的模式与全仓库一致（审查者只是
   不知道惯例）/ 建议与你已知的约束冲突。诚实的无心之失，优雅驳回。

## 第六条（本 skill 自有）：多路共识是优先复核信号，不是免检金牌

多个审查 agent 同报一个问题，通常高于单路的置信——但「独立性」
有限：同源模型共享训练先验，章程不重叠只去相关了注意力，去相关
不了判断误差（多路可能因同一个先验而同错，也可能因同一个盲区
而同漏）。所以处置规则是：**共识 finding 优先复核**（先验证再决定
修/驳），而非「难驳回」；驳回时指出各路共享的同一错误前提即可，
不要求比单路更强的证据级。（单路运行无共识信号，按常规标准。）

## 安全 finding 的驳回白名单

五条过滤原则中「hypothetical vs. actual」**不适用于安全 finding**：
「当前追不到攻击路径」不是安全证据——攻击者的工作就是创造路径。
安全 finding 的驳回证据标准是威胁建模级：资产明确不存在 / 入口
已枚举穷尽 / sink 实际不可达，三者居一才可驳回；拿不到就修或
标注残留风险交用户。

## 什么时候审查者是对的

别因为 finding 刺耳就驳回。该重视的信号：

- 多路同报（优先复核）；
- finding 指出的是具体执行路径，不是假想；
- finding 暴露了你心智模型的缺口（读完你的反应是「……对哦」）；
- **安全 finding 和正确性 bug 即使单路也要加倍认真**——这两类
  误放行的代价远大于误修复。

另外警惕自己的反面漂移：lead 同时是代码作者，第 4 轮疲劳后的
驳回倾向会不自觉地上升——驳回率明显高于前几轮时，把最近两条
驳回拿出来重读一遍再继续。

## 裁决输出格式（进收口报告的处置台账）

每轮处置完输出台账，格式固定、可审计：

```
| # | 级别 | finding | 分类 | 一句话理由/动作 | 置信 | 确认状态 |
| 1 | major | 替换式样式覆盖丢继承（暗色不可见） | 修 | 合并式样式叠加保继承 | 多路共识 | 已确认 |
| 2 | nit   | 图标尺寸两处不一 | 顺手修 | 统一尺寸 | 单路 | — |
| 3 | minor | 常量应收敛到配置对象 | 落档不改 | 各 app/模块各自持有品牌事实源是仓库惯例 | 单路 | 已默许 |
| 4 | nit   | 品牌名应走词表 | 驳回 | 品牌名不译，与仓库既有先例一致（原则：换我不会这么写） | 单路 | — |
```

「确认状态」列跟踪落档/驳回项与审查者的闭环：待确认 / 已默许（发过
复查消息、对方未提异议）/ 已确认（对方明确同意）/ 重提（对方再次提及）。

**重提处理**：审查者在后续轮重提已默许项（它上下文里存着自己的原报告，
重提很自然）→ 引用上轮台账记录请其明确表态，不重复给理由、不重开处置；
它给出新证据时才重新裁决。

台账同时是 PR 描述里「审查记录」节的原料——合并后可追溯当时为什么
这么改。**逐轮落盘**：每轮处置完即写入 PR 描述（或本地台账文件），
不要等收口才写——会话中断时逐轮落盘的台账是唯一的可恢复状态。
