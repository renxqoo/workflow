# 修复循环的处置判断

只读审查输出核实后的发现，不自行修复。进入已获授权的修复循环后，主会话负责结合完整需求和证据裁决，不机械执行审查者建议。

## 分类

| 分类 | 条件 | 处置 |
| --- | --- | --- |
| 修复 | 问题已证实且在本次修复范围内 | 消除根因，使用最小充分改动并验证 |
| 范围内低成本修正 | 有实际价值，且不扩大本次范围 | 与本轮修改一起验证，不因便宜而擅改无关代码 |
| 记录未修 | 有问题但超出授权、需要产品选择或环境不可得 | 记录证据、理由、影响和下一步；不自动建票 |
| 驳回 | finding 的前提或推论被证据推翻 | 说明错误前提及支持证据，不用“我不同意”代替核实 |

不能因多轮疲劳而把未解决问题改称 nit。严重性取决于实际后果和明确契约；纯风格偏好不阻塞交付。

## 过滤问题

- **实际可达性**：触发输入、调用方和状态是否能出现？上游校验和类型约束是否真覆盖运行时边界？
- **具体后果**：命名/结构建议能说明当前错误或可证实的维护成本吗？“我会这样写”不是缺陷。
- **必要抽象**：现有结构是否阻碍正确修复？没有已知变化原因时，不为未来可能性预建层次。
- **完整上下文**：用户要求、目标契约、已有迁移范围是否改变判断？惯例不能为真实缺陷免责，当前测试也可能错误。
- **多路信号**：同报优先核实，但可能共享错误前提；不同结论先检查证据和范围，不能按票数裁决。

安全发现同样需要合理威胁模型、入口到敏感操作的路径或明确缺失的防护。不能用“当前用户不这样用”排除攻击输入，也不能仅因无法彻底证明安全而把无限猜测变成阻断项。证据不足时说明不确定性和进一步验证所需条件。

## 处置台账

按任务规模在最终报告或已允许的本地文档记录：finding、证据、分类、理由/改动、当前版本、验证结果、复查状态。只有已授权回写 PR 才更新外部台账。

状态使用“待确认 / 已明确确认 / 有异议 / 未能复查”。审查者明确的整体通过可覆盖列出的全部处置；没有回应、只检查一部分或未读取当前版本都不是默认认可。

预算耗尽后如实列未确认和未修项。不要把“已发消息”“对方未反对”或“没有新改动”写成通过。
