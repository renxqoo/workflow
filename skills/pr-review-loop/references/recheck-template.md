# 复查消息模板

发给**原**审查 agent（上下文连续，不换新 agent）。消息要短——
只带增量信息，不重贴 rubric，不重新解释背景（Guard the Context Window）。

复查只问「通过 / 不通过 + 理由」，明确禁止展开新审查面——这是防循环
膨胀的关键约束。

---

复查请求（第 {N} 轮）

你上轮报告的问题已处置，最新代码已推送：commit {HASH}（分支 {BRANCH}）。
请跑 `git diff {BASE}...{BRANCH}` 看最新状态后复查。

## 已修（对应你报告的 finding）

- [finding 短引用] → 修法一句话 + 位置
- ...

## 顺手修（未在你报告内，随本轮一并改了）

- ...（没有则删掉本节）

## 落档不改（请你确认理由是否成立）

- [finding 短引用]：不改理由一句话
  （例：包内无既有图标品类，2 处消费不构成收口，开了才是并行架构）
- ...

## 驳回（引用过滤原则）

- [finding 短引用]：原则 = hypothetical vs. actual；证据 = 调用方 X 在
  file:line 已校验，该输入不可能为 null
- ...

## 复查要求

只判断：上述处置是否解决了你报告的问题、修复本身有没有引入新问题。
输出「通过」或「不通过 + 具体理由」。不要展开新的审查面——新观察
（如果真有）用一句话附注即可，留待下轮正式处理。

---

## 发送节奏备忘（主会话用，不进 agent 消息）

- 修复 → 验证命令全绿 → commit → **push 之后**才发复查（复查看远端）；
- 多路审查时每路独立发复查；一路通过另一路不通过，只对不通过那路继续
  循环，通过那路不重开（除非后续修复可能波及其范围——波及时附注请其
  重看相关文件）；
- 「落档不改」和「驳回」只在**首次**出现时请求确认；复查者未反对即视为
  接受，后续轮次不再重复。
