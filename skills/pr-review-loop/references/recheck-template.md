# 复查消息模板

发给**原**审查 agent（上下文连续，不换新 agent）。消息要短——
只带增量信息，不重贴 rubric，不重新解释背景（省 context，审查者的
注意力也是预算）。

复查只问「通过 / 不通过 + 理由」，明确禁止展开新审查面——这是防循环
膨胀的关键约束。

---

复查请求（第 {N} 轮）

你上轮报告的问题已处置，最新代码已推送：commit {HASH}（分支 {BRANCH}，
当前 HEAD）。
请取最新 diff 复查：先 `git fetch origin {BASE} {BRANCH}`，然后
`git diff origin/{BASE}...origin/{BRANCH}`（三点点为空时降级
`git diff $(git merge-base origin/{BASE} origin/{BRANCH})..origin/{BRANCH}`，
仍不可得则告诉我，不要对空 diff 出结论）。

{本轮无代码改动时：开头注明「本轮无代码改动，仅处置确认」，HASH 填
当前 HEAD——全落档/全驳回轮同样要发复查，否则该路永远拿不到结论。}

- ...

## 顺手修（未在你报告内，随本轮一并改了）

- ...（没有则删掉本节）

## 落档不改（请你确认理由是否成立）

- [finding 短引用]：不改理由一句话
- ...

## 驳回（引用过滤原则）

- [finding 短引用]：原则 = hypothetical vs. actual；证据 = 调用方 X 在
  file:line 已校验，该输入不可能为 null
- ...

## 复查要求

只判断：上述处置是否解决了你报告的问题、修复本身有没有引入新问题。
输出「通过」或「不通过 + 具体理由」。不要展开新的审查面——新观察
（如果真有）用一句话附注即可，留待下轮正式处理。

---

## 发送节奏备忘（主会话用，不进 agent 消息）

- 修复 → 验证命令全绿 → commit → **push 之后**才发复查（复查看远端）；
- **零改动轮同样发复查**（全落档/全驳回时）：不 push 无新 commit，HASH
  填当前 HEAD——该路需要显式的「通过」才能结清，沉默不是通过；
- 多路审查时每路独立发复查；一路通过另一路不通过，只对不通过那路继续
  循环，通过那路不重开（除非后续修复可能波及其范围——波及时附注请其
  重看相关文件）；
- 「落档不改」和「驳回」只在**首次**出现时请求确认（按 finding 计）；
  复查者未反对即视为已默许，记入台账确认状态列，后续轮不再重复。
  复查者重提已默许项 → 引用台账记录请其明确表态（见 lead-judgment）。
