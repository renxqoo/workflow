# 风险路判定表 + 各路章程

先判定，后组路。只组命中的路（路 A 恒定之外加 1-2 路，最多共 3 路）。
判定依据是 diff 实际触碰的东西，不是 PR 标题说什么。

## 实质性过滤（判定表前先过这一关）

判定表的字面命中会高估路数——大量「字面命中」不是该路要审的实质。
逐条过滤：

- **契约面**：仅包的公共导出面（JS 的 `exports` / Python 的公开 API /
  Go 的导出符号 / C 的头文件）/ API DTO / schema / 事件定义算。
  应用或模块内部导出、加字段不破坏外部消费者，不算；
- **配置键**：仅部署可变值（env 变量 / 配置解析校验——zod、pydantic 等——/
  运行时可覆盖项）算。硬编码品牌常量（URL、名称）只是代码组织问题，不算；
- **UI 面**：组件结构 / 交互状态 / 样式系统算。纯类名微调与单行文案改动
  de minimis，不单开 UI 路（此类改动的检查点在路 A 章程的维度 3「意图
  对齐」下附带覆盖）。

## 判定表

| diff 特征（实质性命中即组该路） | 组哪路 |
| --- | --- |
| 动了 UI 组件结构 / 交互状态 / 样式系统 | UI 与前端体验路 |
| 动了锁/事务/缓存失效/后台任务/共享可变状态 | 并发与一致性路 |
| 动了包的公共导出面 / API DTO / schema / 事件契约 | 消费方影响面路 |
| 动了 auth / crypto / 输入解析 / 权限判断 / 外部输入到危险 sink | 安全路 |
| 动了外部调用（DB/缓存/第三方）/ schema 迁移 / 部署配置 / 新后台任务 / 错误处理路径 | 生产可用性路 |
| 新增循环内计算 / 数据量级语义变化 / 算法复杂度变化 | 性能与量级路 |
| **以上都不命中** | 结构完整性与可维护性路（缺省路 B） |

**Tie-break**：过滤后仍命中 >2 路时，按风险权重取前二（资损/数据损坏 >
安全 > 正确性 > 其他），舍弃的路写一句进组路记录（可审计，复查时可翻案）。

**兜底信号**：路 A 报告里出现「新增静默 catch」「新增无日志分支」「新增
无上界缓存」任一信号 → 即使判定表没命中，补组生产可用性路（允许临时
第 4 路，从当前轮起算并行结清，不回溯旧轮）。触发靠信号，不靠人记。

## UI 与前端体验路

改的是用户直接看到的东西。机器测不到「看起来对不对」。

- **视觉一致性**：新元素与相邻元素的颜色 token、字号、间距、圆角是同一套吗？
  hover/focus/active 状态都有吗？还是只有默认态？
- **主题与暗色**：亮色下对，暗色下还对吗？颜色是继承语义色（CSS 的
  `currentColor`/设计系统语义 token）还是硬编码了只在一种主题下成立的色值？
  警惕替换式样式类覆盖丢掉继承类（尺寸类之外的颜色/填充类）。
- **可访问性**：图标按钮有可访问名吗（Web 的 aria-label / 移动端的
  accessibilityLabel / contentDescription）？装饰性图形对读屏器隐藏了吗？
  纯图标链接的可访问名从哪来？键盘/焦点能到达吗？
- **i18n**：硬编码文案该走词表吗（品牌名/产品名通常不译，合理）？
  若仓库有 parity 测试，新增键双侧同步了吗？复数/插值形态对吗？
- **布局边界**：窄屏堆叠、超长文本溢出、空数据态、加载态都成立吗？
- **SSR 与 hydration**：客户端指令缺失或多余？server 端用了浏览器 API？
  hydration mismatch 面（Date.now / random / locale 直染）？
  （词汇以 React 为准；非 React 仓库按等价概念映射——SSR 框架对应物 /
  模板引擎直染 / 框架的客户端边界标记。）

## 并发与一致性路

这类 bug 不出现则已，一出现就是数据损坏或资损。

- **原子性**：相关更新能停在半应用状态吗？该进事务的没进？
- **竞态窗口**：check-then-act 之间状态能被改吗（TOCTOU）？并发认领
  同一资源时谁是裁判（DB 唯一约束/乐观锁/悲观锁/队列）？
- **缓存一致性**：写路径和缓存失效在同一事务边界内吗？失效失败会留下
  多久的脏读窗口？
- **重入与重试**：任务重试会重复副作用吗？幂等键真的唯一吗？重试风暴
  会不会对已故障上游加倍施压？
- **顺序依赖**：跨进程事件消费者假设了不保证的顺序吗？

**证据要求**：每条 finding 给出具体交错序列（T1 做什么 → T2 做什么 → 坏在哪）。
「可能有竞态」不算 finding——追不到具体交错就不是。

## 消费方影响面路

契约变更的破坏力在 diff 之外。grep 调用方是起点，不是终点——终点是
grep 看不到的（跨仓库、反射、配置驱动、文档承诺）。

- **导出面变更**：删了/改了签名/改了语义的导出，所有调用方处理了吗？
  逐个搜索生产者、消费者、测试、文档；
- **DTO/字段**：新增字段消费方会忽略还是崩？删除字段有消费方吗？
  序列化形态（wire format）变了吗？
- **schema 变更**：有配套迁移吗（SQL 迁移 / NoSQL 索引与结构版本化 /
  序列化格式演进）？迁移前向吗（旧代码读新库/新代码读旧库）？
  回滚路径是什么？
- **语义漂移**：签名没变但行为变了（单位、时区、null 含义、错误码映射）——
  这是最阴的破坏，编译器不叫；
- **废弃路径**：留了双轨/兼容别名吗？没有拆除日期的双轨是 finding
  （不是可选项）。

## 安全路

新增或改动了攻击面可达的代码。

- 外部输入流向危险 sink（SQL、shell、eval、innerHTML、路径拼接）没有净化；
- 新端点的认证/授权缺口；水平越权（IDOR：拿别人的 ID 能读别人的数据吗）；
- 密钥/凭证出现在代码、日志、错误消息里；
- TOCTOU 在安全关键路径上；
- 反序列化不可信数据；SSRF 面（用户可控 URL 被服务端请求）。

**证据要求**：展示输入到 sink 的完整路径。只断言「这里有 XSS 风险」
既无法核实也无法定位修点——追不到路径就不是 finding。

## 生产可用性路

新代码上线后，值班的人靠什么发现它坏了、止血它坏了？

- **可观测性**：新路径上的失败有日志/metric/trace 吗？错误是结构化的
  还是裸字符串？**静默 catch（吞错继续跑）在本路 = blocker——坏了没人知道**；
- **失败模式**：新增外部调用挂掉时代码去哪？超时设了吗？重试有上限吗？
  重试会不会放大故障？
- **回滚路径**：这改动可回滚吗？schema 迁移不可逆吗？「先双轨跑着看」
  有没有观测指标、删除条件、回滚方案——没有拆除日期的过渡态是 finding；
- **资源上界**：新循环/缓存/队列有内存或条目上界吗？慢查询会锁大表吗？
  批处理有没有分页，还是一口气读全量？

**证据要求**：指出「坏了怎么发现」时给出具体日志语句或 metric 名——
「应该有监控」不算。

## 性能与量级路

- 新的热路径复杂度：循环内查询/IO（典型如 N+1 查询、循环内分配大对象）；
- 数据量级语义：这代码在 10 行数据下对，100 万行下还对吗？分页了吗？
- 无上界的增长：缓存、列表、并发数有 cap 吗；
- 阻塞与串行：独立 IO 被无谓串行了吗（可并行的没并行）；
- 但注意：micro 优化不是本路的事——只报量级语义问题，不报常数因子。

## 结构完整性与可维护性路（缺省路 B）

都不命中风险路时的底线章程。

- **边界纪律**：校验在系统边界做一次，还是散落在业务逻辑里？
- **归属正确**：这段逻辑住在对的层/包/模块吗？还是 feature 逻辑漏进共享层、
  实现细节漏穿 API？
- **复用 vs 重复**：现有 helper 能用却写了个 one-off？同一事实两处定义？
  （反过来：为单一调用点引入抽象 = 过度抽象，也是 finding。）
- **双轨路径**：同一任务出现了第二种做法？旧做法删了吗？
- **融合度**：这段改动像是设计之初就预留了位置，还是硬钉上去的？
  （换个问法：这个需求如果从项目第一天就已知，代码会长这样吗？）
- **数据结构贴合**：数据结构与实际访问模式匹配吗？错的结构会让下游
  每一步都在跟它搏斗；
- **文件规模**：单文件显著膨胀（如跨过 1000 行）而没有结构性理由；
- **可读性**：直接、无趣、可维护 > 机巧魔法。脆的 ad-hoc 行为要标出来。

注意本路的谦抑性：结构建议类 finding 默认封顶 minor——除非它引入了
实际的耦合错误或双轨，否则不升级。
