# 风险路判定表 + 各路章程

先判定，后组路。路 A（正确性）恒定；风险路只组命中的，路数权衡见
SKILL.md 阶段 2。判定依据是 diff 实际触碰的东西，不是 PR 标题说什么。

## 实质性过滤（判定表前先过这一关）

判定表的字面命中会高估路数——大量「字面命中」不是该路要审的实质。
过滤的目的只是**控制专路数量**（审查预算有限），不是豁免检查：
被过滤掉的面不消失，降为路 A 的附带检查项（各条目内已标注去向）。
逐条过滤：

- **契约面**：只有「会被本包之外的代码依赖的东西」才算——包对外声明的
  公共接口、跨进程的 API/DTO、schema、事件定义。判据是**有没有下游
  会受影响**，不是导出修饰符：模块内部导出一旦被别处 import，它就是
  事实上的契约；纯私有实现怎么改都不算；
- **配置键**：只有「部署时可变、改变运行行为的值」才算——环境变量、
  配置文件的解析校验、运行时可覆盖项。写死在代码里的常量（URL、名称、
  阈值）不单开专路，但不是不查：常量值本身的正确性（URL 拼写、域名、
  版本号）在路 A 维度 1「正确性」下附带验证；
- **UI 面**：组件结构 / 交互状态 / 样式系统算。纯样式微调与单行文案改动
  不单开 UI 路，但样式改动的继承链影响（替换式覆盖丢掉继承的颜色/填充
  ——暗色主题下不可见的经典形态）与文案的正确性在路 A 维度 1 附带检查。

**拿不准就不过滤**：过滤规则拿不准时，宁可多开一路。过滤着错 = 漏审；
多开一路 = 多花一份审查预算，且 lead-judgment 的过滤原则会清掉误报。

## 判定表

| diff 特征（实质性命中即组该路） | 组哪路 |
| --- | --- |
| 动了 UI 组件结构 / 交互状态 / 样式系统 | UI 与前端体验路 |
| 动了锁/事务/缓存失效/后台任务/共享可变状态 | 并发与一致性路 |
| 动了会被外部依赖的接口（含事实契约）/ 数据 schema / 事件契约 | 消费方影响面路 |
| 动了 auth / crypto / 输入解析 / 权限判断 / 外部输入到危险 sink | 安全路 |
| 动了外部依赖（数据库/缓存/第三方服务）/ schema 迁移 / 部署配置 / 新后台任务 / 错误处理路径 | 生产可用性路 |
| 新增循环内计算 / 数据量级语义变化 / 算法复杂度变化 | 性能与量级路 |
| **以上都不命中** | 结构完整性与可维护性路（缺省路 B） |

表里的词按本项目技术栈解读（Web 项目把「UI 组件」读作组件框架的组件，
其他项目读作等价物——模板、视图、界面声明）。

**Tie-break**：命中路数超出你决定的组路数时，按风险权重取前几（资损/
数据损坏 > 安全 > 正确性 > 其他），舍弃的路写一句进组路记录（可审计，
复查时可翻案）。

**兜底信号**：路 A 报告里出现「新增静默吞错」「新增无日志分支」「新增
无上界缓存」任一信号 → 即使判定表没命中，补组生产可用性路（同样受
路数裁量约束，从当前轮起算并行结清，不回溯旧轮）。触发靠信号，
不靠人记。

## UI 与前端体验路

改的是用户直接看到的东西。机器测不到「看起来对不对」。

- **视觉一致性**：新元素与相邻元素的颜色、字号、间距、圆角是同一套
  设计系统吗？交互状态（悬停/聚焦/按下）都有吗？还是只有默认态？
- **主题与暗色**：亮色下对，暗色下还对吗？颜色是继承语义色/设计系统的
  token，还是硬编码了只在一种主题下成立的色值？警惕替换式样式覆盖
  丢掉继承来的颜色/填充——暗色主题下图标变黑消失的经典形态；
- **可访问性**：图标按钮有可访问名吗？装饰性图形对读屏器隐藏了吗？
  纯图标链接的可访问名从哪来？键盘/焦点能到达吗？（具体属性名按
  平台——Web 的 aria-* / 移动端的 accessibility 标注——不用挨个对号，
  问题本身跨平台成立）；
- **i18n**：硬编码文案该走词表吗（品牌名/产品名通常不译，合理）？
  若仓库有词表同步校验，新增键各语言侧同步了吗？复数/插值形态对吗？
  （单行文案本身的对错与语法由路 A 兼管——本路只管归属与同步）；
- **布局边界**：窄屏堆叠、超长文本溢出、空数据态、加载态都成立吗？
- **服务端渲染**：客户端/服务端代码边界对吗（该跑在服务端的用了
  浏览器 API？该水合的两侧不一致——时间/随机值/地区设置直染——
  会产生 hydration mismatch 类缺陷）？没有服务端渲染的项目跳过这条。

## 并发与一致性路

这类 bug 不出现则已，一出现就是数据损坏或资损。

- **原子性**：相关更新能停在半应用状态吗？该进事务的没进？
- **竞态窗口**：check-then-act 之间状态能被改吗（TOCTOU）？并发认领
  同一资源时谁是裁判（唯一约束/乐观锁/悲观锁/队列）？
- **缓存一致性**：写路径和缓存失效在同一事务边界内吗？失效失败会留下
  多久的脏读窗口？
- **重入与重试**：任务重试会重复副作用吗？幂等键真的唯一吗？重试风暴
  会不会对已故障上游加倍施压？
- **顺序依赖**：跨进程事件消费者假设了不保证的顺序吗？

**证据要求**：每条 finding 给出具体交错序列（T1 做什么 → T2 做什么 → 坏在哪）。
「可能有竞态」不算 finding——追不到具体交错就不是。

## 消费方影响面路

契约变更的破坏力在 diff 之外。grep 调用方是起点，不是终点——终点是
grep 看不到的（跨仓库、反射、配置驱动、文档承诺）。

- **接口变更**：删了/改了签名/改了语义的对外接口，所有调用方处理了吗？
  逐个搜索生产者、消费者、测试、文档；
- **DTO/字段**：新增字段消费方会忽略还是崩？删除字段有消费方吗？
  序列化形态（wire format）变了吗？
- **schema 变更**：有配套迁移吗？迁移前向吗（旧代码读新库/新代码读旧库）？
  回滚路径是什么？
- **语义漂移**：签名没变但行为变了（单位、时区、null 含义、错误码映射）——
  这是最阴的破坏，编译器不叫；
- **废弃路径**：留了双轨/兼容别名吗？没有拆除日期的双轨是 finding
  （不是可选项）。

## 安全路

安全 finding 的特殊性：误报的代价是几行代码，漏报的代价是事故——
所以本路宁可多疑，由主会话的过滤原则去清误报。

- 外部输入流向危险 sink（查询语句拼接、shell 执行、动态求值、
  标记注入、路径拼接）没有净化——具体 sink 按技术栈识别；
- 新端点的认证/授权缺口；水平越权（IDOR：拿别人的 ID 能读别人的数据吗）；
- 密钥/凭证出现在代码、日志、错误消息里；
- TOCTOU 在安全关键路径上；
- 反序列化不可信数据；SSRF 面（用户可控 URL 被服务端请求）。

**证据要求**：展示输入到 sink 的完整路径。只断言「这里有注入风险」
既无法核实也无法定位修点——追不到路径就不是 finding。

## 生产可用性路

新代码上线后，值班的人靠什么发现它坏了、止血它坏了？

- **可观测性**：新路径上的失败有日志/指标/链路追踪吗？错误是结构化的
  还是裸字符串？**静默吞错（吞掉继续跑）在本路 = blocker——坏了没人知道**；
- **失败模式**：新增外部调用挂掉时代码去哪？超时设了吗？重试有上限吗？
  重试会不会放大故障？
- **回滚路径**：这改动可回滚吗？schema 迁移不可逆吗？「先双轨跑着看」
  有没有观测指标、删除条件、回滚方案——没有拆除日期的过渡态是 finding；
- **资源上界**：新循环/缓存/队列有内存或条目上界吗？慢操作会锁大表吗？
  批处理有没有分页，还是一口气读全量？

**证据要求**：指出「坏了怎么发现」时给出具体日志语句或指标名——
「应该有监控」不算。

## 性能与量级路

量级错误的特征是测试全绿、上线才爆——10 行数据的测试证明不了
100 万行的行为。

- 新的热路径复杂度：循环内查询/IO（典型如每行一次查询、循环内分配
  大对象）；
- 数据量级语义：这代码在 10 行数据下对，100 万行下还对吗？分页了吗？
- 无上界的增长：缓存、列表、并发数有 cap 吗；
- 阻塞与串行：独立 IO 被无谓串行了吗（可并行的没并行）；
- 但注意：micro 优化不是本路的事——只报量级语义问题，不报常数因子。

**证据要求**：报量级问题要给量级估算依据（调用频次 × 单次成本 /
预期数据规模）——拍脑袋的「可能慢」不算。

## 结构完整性与可维护性路（缺省路 B）

都不命中风险路时的底线章程。

- **边界纪律**：校验在系统边界做一次，还是散落在业务逻辑里？
- **归属正确**：这段逻辑住在对的层/包/模块吗？还是 feature 逻辑漏进共享层、
  实现细节漏穿 API？
- **复用 vs 重复**：现有 helper 能用却写了个 one-off？同一事实两处定义？
  （反过来：为单一调用点引入抽象 = 过度抽象，也是 finding。）
- **双轨路径**：同一任务出现了第二种做法？旧做法删了吗？
- **融合度**：这段改动像是设计之初就预留了位置，还是硬钉上去的？
  （换个问法：这个需求如果从项目第一天就已知，代码会长这样吗？）
- **数据结构贴合**：数据结构与实际访问模式匹配吗？错的结构会让下游
  每一步都在跟它搏斗；
- **文件规模**：单文件显著膨胀（如跨过千行）而没有结构性理由；
- **可读性**：直接、无趣、可维护 > 机巧魔法。脆的 ad-hoc 行为要标出来。

注意本路的谦抑性：结构建议类 finding 默认封顶 minor——除非它引入了
实际的耦合错误或双轨，否则不升级。
