# To spec

把已经讨论的需求与决策整理成可执行规格，不重新开启完整访谈，不凭空补齐未知需求。以用户明确要求确定目标，以仓库代码、测试和配置核实现状；使用项目术语并核对相关架构约束。

## 整理流程

1. 提取问题、目标用户、已确认行为、范围和决策。将用户要求、当前事实、建议及未决事项分开；旧文档与实现冲突时说明差异。
2. 只补充影响规格的仓库调查。定位现有能力、受影响模块、公开接口及测试入口，不把尚未确定的 HTTP、数据结构或外部服务当成既定契约。
3. 按复杂度写规格。简单变更用几段即可；复杂功能按下列内容组织，删除不适用项，不强制长故事列表或固定章节。
4. 检查每项要求是否有可观察的验收方式，是否存在相互矛盾的决定，未决事项是否会阻碍实施。已有测试入口优先，跨边界行为在对应层级验证，不以测试入口越少或越高作为目标。
5. 默认保存到项目已有的本地规格目录；没有约定时选择清晰的本地文档位置并在交付中注明。只写规格，不默认开始实现。

## 规格内容

- **问题与目标：** 用户遭遇什么问题，完成后能做到什么。
- **范围与非目标：** 已明确包含和排除的内容，不用假想需求扩张边界。
- **行为与验收：** 必要的用户流程、业务规则、边界和异常反馈。用户故事只在帮助表达需求时使用，每项要能判断是否完成。
- **实现决策：** 已确认的模块职责、接口、状态、数据和交互约束。区分确定方案与待选方案；路径或短代码片段能消除歧义时可用，但不能以实现细节代替需求。
- **验证方案：** 哪些行为在哪个层级验证、可复用的现有用例和仍缺的设施。期望来自独立需求，验证外部行为，不照抄常量或实现逻辑。
- **未决事项：** 缺失信息、影响、可选方案及有依据的建议。非阻塞项明确标注假设；阻塞项不能伪装成已确定。

仅当缺失信息会实质改变范围、外部契约或验收时，提出简短的必要问题，并继续整理不受影响的内容。不要求每次确认测试入口，也不依赖某个 setup 技能。

## 发布边界

只有用户明确要求把规格发布为工单或写入指定外部系统，才执行相应写入；沿用本次任务已有的授权。发布前核对目标项目、内容与实际标签约定，不自动加 ready-for-agent 等标签，不把未回复当成同意。

发布信息不全时先交付可审阅的本地规格，明确尚缺信息。若要定位、去重和管理已有问题，可按需使用可用的 to-issue 工作流，但它不是本技能的前置条件。

交付时给出本地文档位置，或实际已授权发布的工单链接，并指出影响执行的未决事项。
