# Why

回答“为什么这样设计”“为什么选这个阈值”“这段防御逻辑从何而来”。当前代码用于确定调查对象，动机需要提交、评审、工单、设计文档或讨论等记录支持。只读调查，不因解释请求修改代码、发布消息或变更外部状态。

## 调查流程

1. 确定目标与问题，从上下文定位文件、关键符号及决策；范围不明确时说明采用的解释。按[证据分级](references/epistemics.md)区分事实与解释，用户自带的假设也需要核验。
2. 建立代码锚点：核对当前实现，按需用 git log、blame 与相关 diff 找到引入或修改行为的提交，提取可查的 PR、工单和日期。仓库没有历史或工具不可用时记录限制，不假定 git 或 gh 一定可用。
3. 根据问题、已有线索与当前可用工具选择来源。先追踪直接关联的记录；按[来源索引](references/source-playbook.md)扩展相关调查，不要求遍历全部服务。防御逻辑或事故线索可参考[事故调查](references/sources/incident-postmortem.md)。
4. 有可独立调查的来源时，可用当前宿主的实际委派工具并行，默认继承模型。使用[调查提示](references/investigator-prompt.md)交代问题、代码锚点和分工；无委派工具或目标很小，直接完成。
5. 交叉核对直接证据、时间关系与矛盾。需要整理多路结果时参考[综合提示](references/synthesizer-prompt.md)，核验关键引用，不盲信摘要或代理结论。

调查到足以回答问题、主要矛盾已解释，或相关可用线索已查尽时收束。不为填满来源清单做无关搜索；只有会影响结论的缺失来源才需要指出。

## 交付

先给有证据支持的回答，关键结论附可核对的引用。将明确记录、合理推断、竞争假说和未知分开，说明实际搜索范围及影响结论的缺口；不把未找到证据写成从未发生，也不以当前代码看起来合理反推作者意图。

若用户准备修改这段代码，可补充证据支持的保留约束、可变部分和风险。调查结论不自动授权后续修改。
