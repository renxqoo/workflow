# 测试与验证

## 确定行为入口

先查看受影响测试、配置和实际调用，选择能观察业务结果的稳定接口。纯计算可以通过函数接口验证；流程缺陷要覆盖实际调用和状态转换，不能只测提取出的辅助函数。

期望值来自独立业务规则、明确契约、人工算例或已确认样例。不要照抄实现算法、断言常量等于声明值，或只断言测试自行构造的数据。配置承载的公共约束和跨数据一致性仍可测试，前提是能指出违反什么真实规则。

## 按相关风险选用例

- 正常路径验证调用方能观察的结果及必要副作用。
- 外部输入按契约验证拒绝、错误反馈或容错；允许契约规定的抛错，不要求垃圾输入一律静默成功。
- 涉及异步时覆盖相关取消、超时、晚到结果、重复触发与资源清理，使用确定性调度或合理容差，避免靠长时间等待证明正确。
- 涉及权限隔离时列主体、资源和操作的代表性矩阵，验证未获准数据不可见、未获准操作不生效。
- 枚举、错误表与事件时序只有在属于公共契约时才按独立规格验证；内部类型穷举优先使用项目已有静态检查，不为每个实现分支创建镜像测试。

## 回归与 test-first

修复 bug 时先添加或调整能暴露症状的用例，确认它在缺陷存在时因该缺陷失败，再做充分的根因修复并确认通过。无法取得失败证据时记录原因与替代验证。

用户明确要求 test-first 时，逐个可观察行为执行失败测试、充分实现、再验证的短循环，避免先批量编写想象中的测试再整体实现。`tdd` 可用时参考；缺少该技能不影响执行本节。

内部重构而行为不变时，行为测试应继续通过。目标行为确已改变时可以同步更新测试，但须给出需求依据，不能以实现现状作为降低断言的理由。

## 检查范围与覆盖率

- 从目标项目实际脚本、测试配置和 CI 取得入口、覆盖率范围与指标，不复制其他仓库的阈值或自行增加门禁。
- 实现中运行相关用例与检查；阶段、提交或交付时按项目要求运行完整门禁。修改了装置、共享状态或公共边界时据影响扩大回归范围。
- 覆盖率不足时先确认未覆盖行为和统计范围，再补有意义的验证；不得降低阈值、缩窄范围或添加空转断言换绿。需要改变门禁本身时须有独立任务依据与授权。
- 分别报告实际测试结果、适用的用例数、覆盖率数字和配置内门禁结果；未运行的检查明确说明。已有失败按证据归属，失败不能被描述为完整门禁通过。

## 集成与浏览器验证

复用项目现有入口，围绕受影响的用户旅程或跨边界行为增加验证。断言业务终态、错误反馈和清理结果，而不只断言状态码或“未崩溃”。装置不足时先说明缺口，补最小可复用能力，不为局部改动引入平行体系。

需要真实凭证、付费或操作共享环境的检查先核对授权。替身结果与真实上游结果分别报告，未执行真实检查时说明限制，不把它当作所有功能的无条件收口要求。
