# 独立审查

用于发现实现者上下文容易忽略的规格缺口。契约、权限、并发、资源生命周期和大范围改动优先安排；局部低风险改动按项目要求决定。

## 输入与角色

使用当前宿主可用的独立会话或子代理，默认继承模型；不假定某个工具、模型或服务存在。审查者只读，不承担实现修改。没有独立能力时记录限制，不能把自查称作独立审查或绕过项目要求。

提供：

- 最终 diff、必要上下文及可读取的目标仓库位置。
- 用户目标、已确认契约、范围边界及项目约束。
- 测试依据、风险清单和已执行验证的原始结果。

不要求审查者接受实现过程中的结论；允许其沿调用链核实遗漏，避免只读孤立片段而误判。

## 审查任务

> 检查改动是否违反目标契约，是否在边界、错误路径、权限、并发或清理时出错。每项发现给出位置、触发条件、可观察后果与证据；区分已确认缺陷和待验证疑点。不为迎合“必有 bug”捏造问题，不把个人风格偏好当作缺陷。

也检查测试是否因缺陷而失败、是否验证了实际入口，及装置是否绕开真实接缝。若断言变动，核对需求变化或装置适配依据。

## 顺序与处置

先执行适用检查排除机械错误，再审查最终改动。高风险批次分别审查；机械且同风险面的小批次可合并，不能因此略过未审查的高风险变化。

每项发现由实现侧复现、修复，或附证据驳回；待确认风险如实保留，不凭审查者语气决定。代码修正后重跑受影响检查及项目规定的完整门禁；只有风险仍未解决或明确要求多轮审查时才继续下一轮。

需要明确的多轮 PR 审查时可使用 `pr-review-loop`；不可用时按问题、修正与复查证据迭代即可，不自动发布评论或扩大到推送、合并。
