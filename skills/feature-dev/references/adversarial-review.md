# 对抗审查（Adversarial Review）操作细则

对抗审查解决四门解决不了的问题：**门禁裁判「规格覆盖到的地方」，
审查裁判「规格没覆盖到的地方」**。编译通过、测试全绿的代码仍可能错
——写代码的会话在实现上下文里有自证偏差（它倾向认为自己是对的），
所以审查必须来自独立上下文，并且被明确指示「假设代码是错的」。

## 何时做

- **中级 / 大级**：每个提交批次进门禁前必做；
- **小级**：可选——门禁覆盖足、改动面小时允许跳过（提交说明注明跳过理由）；
- **方案文档定稿前（大级三件套）**：文档本身也要过一轮——方案级的错误
  会放大到每一处实现里，靠测试挂掉才发现就晚了。

## 怎么做（关键：上下文隔离）

1. **新开会话或派子 agent**——绝不复用实现代码的会话；
2. 审查者只喂三样东西，**不给实现过程与推理**：
   - diff（或方案文档全文，审文档时）；
   - 方案对应节选：外部契约、问题域与「不处理」清单、并发/一致性预算；
   - 测试口径（若已定稿）；
3. 指令模板（照抄改语境即可）：

   > 假设这段代码是错的。你的唯一任务是找出它会在哪里坏：边界条件、
   > 错误路径、资源生命周期、并发交错、契约违背、越出方案「不处理」
   > 清单的隐藏职责。逐条列出问题（位置 + 触发场景 + 为什么错），
   > 不评价风格，不建议重构，只找 bug。找不到就明说找不到。

4. 产出问题清单，回到实现侧**逐条处置**：修掉，或驳回并写明理由——
   不允许「看过但不动」；
5. 处置完、若代码有改动则重过四门，然后才提交。

## 审查者护栏

- **角色分离是机制不是建议**：审查者不实现代码，实现者不审查自己；
- 警惕「需要一段话来解释为什么这个 workaround 可以接受」的代码——
  那通常就是不可以接受。打回去修代码，而不是接受一段注释。

## 与四门的顺序

实现 → 四门（先清机械错误，减少审查噪音）→ 对抗审查（抓规格盲区）
→ 逐条处置 → 有改动重过四门 → 提交。
门禁便宜（机器跑），审查贵（独立上下文）——先便宜的，后贵的。
