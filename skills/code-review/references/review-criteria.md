# 日常代码审查准则

本准则帮助核实受审代码的具体问题；diff 审查关注本次引入或暴露的问题，模块审计按指定范围检查现状。默认只读审查；发现问题后给出证据和修正方向，不自动修改实现。
只深入与改动有关的风险，不为覆盖清单、满足数量或展示审查力度制造发现。

## 两个独立判断轴

- **行为与需求正确性**：实现是否满足用户要求、已确认业务规则和公开契约；成功、失败、取消与重复操作是否符合预期。
- **仓库规范与结构质量**：实现是否遵守适用的仓库约束，是否引入可说明的结构和维护成本。

一个轴通过不代表另一个轴通过。反馈应能辨认属于哪个轴；结构偏好不能替代行为证据，行为正常也不能免除明确的仓库约束。
需求依据优先来自用户说明、关联议题、设计或规格；代码和测试用于核实现状，不能自行成为新需求。
缺少需求来源时仍审查可确认的行为和契约，并说明无法完整判断需求符合性；不要把未知解释为已满足或未满足。
仓库依据来自适用的 AGENTS、贡献指南、架构文档、脚本、配置及 CI；核实作用范围和是否仍适用。
仓库明确规范优先于通用维护性启发式。工具已稳定覆盖的格式或机械检查无需逐项重复评论。
若目标明确要求改变旧契约或规范，检查实现、调用方、迁移和文档是否配套，不能把旧状态视为不可更改。

## 先建立可追踪的上下文

沿改动追踪必要的调用方、被调用方、类型、配置和测试，确认输入来源、状态归属、错误传播与真实消费方。
优先查证支撑判断的关键事实：输入是否已校验、删除项是否仍被引用、状态转换是否保持不变量。
区分本次引入的问题、已有缺陷和范围外建议；旧问题只有被改动触发或扩大时，才归因于本次改动。
判断修复是否覆盖已证实的根因。guard、重试、类型断言或新抽象本身不是缺陷；须指出掩盖或制造了什么错误。
不要用未来假设需求扩大审查目标，也不要默认为所有外部调用方保留双轨或删除兼容层。

## 按真实风险深入

以下维度用于选择检查方向，不表示每次审查都要逐项出结论。纯文案、常量、私有重命名和小样式也按其实际影响核实。

### 行为、数据与类型边界

追踪正常与异常路径中的值和状态，重点检查空输入、边界值、数值单位、编码、时区、序列化及错误语义。
类型声明、运行时校验和真实输入必须连起来看；编译期阻止的误用不能当作可达运行时缺陷。
例如，不能只说“这里可能为空”：应找到允许空值的入口，以及该值到达出错操作的调用链。
跨接口、事件或数据格式的改动，追踪真实消费方，指出何种输入、版本或迁移阶段会破坏契约。
对缺失需求、部分实现和额外行为引用相应目标；意图有歧义时明确待确认之处，不暗中选择业务规则。

### 安全与信任边界

先识别受保护资产、身份和信任边界，再追踪实际不可信输入到敏感操作的路径。
按改动检查授权、凭证暴露、注入、路径/网络访问、反序列化、重放和安全关键时序问题。
安全发现应包含攻击者可控制的输入、缺失或无效的防护及可达后果；危险 API 名称本身不构成漏洞。
例如，输入已在可信边界被有效约束时，不能只因下游缺少第二次校验就报告注入。

### 并发、状态与恢复

当多个执行者确实共享可变状态时，检查更新原子性、check-then-act、缓存失效和顺序依赖。
检查异步响应乱序、过期闭包、重复触发、重试、取消及中途失败后，状态是否仍可解释和恢复。
竞态发现需给出具体交错：谁先读写什么、另一执行者如何介入、最终产生什么错误结果。
重入或恢复缺陷需说明前次留下的状态，以及下一次执行如何失败；不能仅以“没有锁”推断并发缺陷。

### 资源与运行可用性

检查本次涉及的连接、文件、句柄、监听器、后台任务和内存是否有明确生命周期与必要的清理。
外部依赖失败时，核实超时、重试边界、取消传播、部分更新、迁移与恢复是否符合目标。
错误必须由合适层次处理或反馈；已有结构化错误、指标或上层提示可能已足够，不要求每个 catch 都记录日志。
指出静默失败如何让用户操作、状态或恢复受损，而不是把吞错语法一概当作阻断问题。

### UI 与用户可观察体验

有相关改动时检查项目实际支持的交互状态、设计系统、主题、窄屏、长文本、键盘、可访问名和焦点。
加载、空态、失败与取消路径应能完成或解释用户操作；服务端渲染场景还需核实浏览器依赖及水合差异。
视觉发现应说明具体状态、平台、对比依据和可观察后果；无法运行时注明静态判断，不凭空新增平台或主题要求。

### 性能与量级

关注实际热路径中的重复 IO、复杂度、阻塞、无界增长及资源放大；结合调用频率和真实数据规模判断影响。
给出已知规模、调用关系或测量依据。没有业务意义的微优化、仅凭“可以并行”提出的改写，不应成为缺陷。
性能验证使用适用的现有方法；普通静态审查不自动扩展成压力测试或新建基准框架。

## 结构质量与维护性

检查职责和逻辑是否在已有的合适层次，公开接口是否暴露内部细节，是否重复维护本应一致的事实或规则。
关注新增的耦合、散落的特例、无当前用途的参数/模式、隐蔽状态以及使调用契约更难理解的类型边界。
名称含混、重复逻辑、数据成组出现、长调用链、纯转发包装等，只是寻找具体成本的启发式。
文档化规范违反应引用适用文件和规则；维护性判断应标明判断性质，并说明当前阅读、修改或一致性成本。
单文件行数、分支数量或抽象数量不能单独证明结构缺陷；是否拆分以仓库规则、职责和实际理解负担为据。
简单直接的代码不因缺少 class、状态机或通用抽象而扣分；重复也不自动要求抽取，抽取本身可能增加耦合。
例如，两处相似代码分别表达独立业务规则时，外形相似不足以要求合并；若它们必须同步维护同一事实，应指出该约束。
提出更简洁结构时说明它消除了什么具体负担及影响范围，不把审查扩展为未经请求的重构或自动修复。

## 验证与发现门槛

测试应验证外部行为、边界、不变量或错误路径，期望值应有独立依据；只复述实现或私有调用顺序不能证明目标正确。
bug 回归测试应能在缺陷存在时失败；契约测试最初通过并不无效。结合已有覆盖判断缺口，不要求每处改动都增加测试或端到端测试。
检查真实结果而非代理信号：缓存、时间戳、任务自述或测试桩不能独自证明目标产物或集成链路正确。
每条有效 finding 必须写清：**可达触发条件 + 具体位置 + 可观察后果或明确约束违反 + 支撑证据**。
证据可以是已追踪调用链、输入与交错、适用规范、命令结果或运行复现；区分静态推断和实际执行结果。
无法验证的关键依赖或环境限制应显式报告，不能把未运行说成通过，也不能把不确定的怀疑写成确定缺陷。
缺少触发条件或后果的疑点先核实；仍不成立时舍弃，必要的待确认事项与已确认发现分开。
发现数量可以为零。无发现只表示在所述范围、版本和验证深度内未发现满足门槛的问题，不表示证明整体无缺陷。
