# 范围、版本与报告

## 选择实际对象

用户明确给出的对象优先。没有指定时，可从当前对话和工作区状态选择并说明：例如“当前未提交改动”包含暂存、未暂存及范围内未跟踪文件；工作区干净不等于用户指定的分支或模块没有内容可审。

| 对象 | 取证方式与边界 |
| --- | --- |
| 某段提交、分支或 PR | 验证实际 ref 能解析，记录基准与被审提交 SHA；需要分支相对变化时用真实 merge-base。不要假定默认分支名 |
| 暂存区 | `git diff --cached`，必要时用 `git show :path/to/file` 读 index 内容；磁盘上的后续修复不属于暂存内容 |
| 当前未提交改动 | 同时看 `git diff`、`git diff --cached`、状态及未跟踪文件；以实际最终工作区内容判断整组变化，不能把已在工作区修正的中间暂存缺陷当最终缺陷 |
| 指定文件或模块 | 读当前内容及必要调用上下文；用户没有要求比较历史时，不强制寻找基准 |
| 没有本地 Git 或远端读取能力 | 对可访问的具体文件记录内容摘要及范围限制，不能假称已审不可访问的 PR 或历史 |

对于提交范围，`git diff <base>...<head>` 展示 merge-base 到被审提交的变化，不包含未提交工作。对于工作区，普通 diff 不包含未跟踪文件，删除或重命名也需核对实际引用和消费者。

检查所有权与授权时，不为取得“干净版本”而暂存、提交、stash、切分支或重置用户文件。必要隔离使用临时副本，清理本次产生的文件，不删除他人的进程或资源。

## 固定与复核版本

按范围记录足够的信息即可：提交 SHA；暂存区的 HEAD、相关 diff 和 index 内容摘要；工作区的 HEAD、状态、相关 diff 及文件内容摘要；或指定模块的内容摘要。摘要使用当前环境可用方式，不要求新增项目脚本。

审查前后核对相同对象。记录不能只依赖 mtime、分支名或 HEAD：未提交文件和 index 可以在 HEAD 不变时变化。只重新检查受影响范围，未变化的证据可以复用。

## 全新上下文独立审查

主 agent 负责派发和最终核实。每次派发均新建子 agent，默认继承当前模型，显式关闭父会话继承；工具提供 `fork_turns` 时设为 `none`，其他工具核实等效选项或独立上下文默认值。新 agent ID 本身不能证明上下文独立；不复用参与过实现或已有审查的会话。

默认两路侧重点互补，各自覆盖完整文件范围并检查基本正确性。低风险小改动允许单路全新子 agent，但须先确认影响局部且不改变行为、契约或关键风险，例如纯文案纠错；单路仍覆盖两个判断维度。只因改动少、测试通过或资源不足，不能认定低风险。高风险改动可按实际风险增加专项审查者。

给各路相同的事实包，仅附不同的审查侧重点：

- 仓库绝对路径、本次用户目标和已确认业务规则。
- 实际审查对象、基准、版本记录、文件范围与排除项；工作区或 index 需包含相应内容摘要。
- 适用的 AGENTS、规格、规范与契约位置，以及必要的调用上下文入口。
- 可用验证命令、临时隔离方式、只读及外部操作权限。
- 回报要求：实际审查版本、两个维度的结论、候选发现的触发条件/位置/后果/证据、已执行验证和未验证项。

首轮不传实现者的自证解释、主 agent 预设的 finding 或其他审查者结论；已确认的需求和约束必须保留。子 agent 根据事实包读取实际材料，首轮互不交换发现，仅完成本路只读审查，不再创建子 agent。此处的两路派发只由主 agent 执行。

主 agent 等待各路完成后核对版本、合并重复发现，并亲自核实支撑结论的关键事实和严重程度。意见相同不代替证据，意见不同按可达条件、契约和实际结果裁决；证据不足的保留为待核实项或舍弃。必要补审仍创建全新子 agent；定向复核可以提供原发现和证据，并明确其复核用途。

并发资源不足时可串行创建两路全新子 agent。无法委派或无法保证全新上下文时，继续完成可做的只读检查，说明实际方式与独立审查限制，不能声称双路独立审查已完成。对不同快照的结论先统一版本再汇总；失败、沉默或超时列为未完成审查，不当作无发现或通过。

## 发现应包含什么

一条可操作发现可以这样写：

```text
[major] 刚好达到折扣门槛的订单未享受折扣
位置：绝对路径及实际行号
依据：本次规则规定数量达到门槛即享受折扣
触发与后果：数量等于门槛时进入不打折分支，订单总额偏高
证据：调用入口、分支条件及定向运行的输入/实际结果
建议：按已确认的包含边界规则修正条件，并增加该症状回归
```

不能只写“有边界问题”“需要空值检查”“缺少测试”。给出实际遗漏行为或坏路径；不能实际运行时明确静态推断，建议不是已完成修复。

严重程度可沿用项目约定；没有约定时按后果区分阻断、实质缺陷、局部风险和建议。风格偏好单独列为可选建议，零发现时不为填格式生成建议。

## 两个维度各自说明结论

小改动可以用两句话，大改动再用分段或表格：

- 需求与行为：发现、已核对规则或未能核实的目标。
- 规范与结构：明确违反、具体维护成本、无发现或缺失的依据。

一个维度没有发现不能抵消另一个维度的缺陷。缺少正式规格时，不把“无规格”归为实现缺陷，也不宣称需求完全符合；已确认的用户目标和实际调用契约仍可作为依据。

最后列实际执行的验证及关键结果、未运行检查和环境限制。若任务涉及测试数量或覆盖率，报告实际数字；没有采集不编造。只读审查不需要为了收口新建测试、安装覆盖率工具或修改 CI。
