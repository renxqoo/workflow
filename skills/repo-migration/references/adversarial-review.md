# 对抗审查（Adversarial Review）操作细则（迁移版）

迁移场景的对抗审查多一个裁判维度：**行为等价**。四门裁判「新旧测试
都绿」，审查裁判「测试够不到的行为偏差」——签名相同语义不同、错误
路径静默化、副作用时序变化、边界条件收窄，这类偏差编译器和测试都
可能放过，只有带着「假设新代码偏离了旧实现」的怀疑者对照旧实现
读 diff 才能抓到。

## 何时做

- **三件套文档定稿前**：DESIGN / IMPLEMENTATION / MIGRATION 各过一轮
  独立审查——假设方案有错：裁决依据是否充分、迁移矩阵有没有漏、
  「不处理」有没有留白。方案级错误会放大到每个迁移单元；
- **分阶段实施的每个提交批次**：先过四门清机械错误，再做对抗审查；
  契约/并发/资源生命周期密集的批次逐批必审，机械性高、规格面小的
  批次（纯函数、表驱动用例）可并入相邻批次合并审或注明豁免——
  但不许整段迁移一路豁免；
- **e2e 装置建成后的首个旅程**：装置本身也要被怀疑——替身行为是否
  失真、断言是否比旧口径弱。

## 怎么做（关键：上下文隔离）

1. **新开会话或派子 agent**——绝不复用迁移实现的会话；
2. 审查者只喂四样东西，**不给实现过程与推理**：
   - 新实现 diff + 对应的**旧实现片段**（行为等价的对照基准）；
   - MIGRATION 文档中该单元的行为规格基线与迁移矩阵行；
   - 装置适配记录（若断言被调整过）；
   - 测试口径；
3. 指令模板（照抄改语境）：

   > 假设这段新代码与旧实现行为不一致。你的唯一任务是找出偏差：
   > 错误路径与静默吞错、边界条件收窄、副作用时序、事件次数
   > （恰好一次变多次/丢失）、并发交错下的语义差、契约默认值漂移。
   > 对照旧实现逐条列出（位置 + 触发场景 + 新旧行为差异），
   > 不评价风格，不建议重构，只找行为偏差。找不到就明说找不到。

4. 产出偏差清单，回到实现侧**逐条处置**：修掉，或证明「这是
   MIGRATION 文档里已裁决的有意变更」并给出节号——不允许「看过不动」；
5. 处置完、有代码改动则重过四门，然后才提交。

## 审查者护栏

- **角色分离是机制不是建议**：审查者不实现代码，实现者不审查自己；
- 警惕「需要一段话来解释为什么这个行为变化可以接受」——那通常就是
  不可接受的行为漂移：要么修代码，要么回 MIGRATION 文档补裁决；
- 断言被改过但装置适配记录里查无此项 → 直接打回。
