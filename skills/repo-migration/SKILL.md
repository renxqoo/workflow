# 仓库与架构迁移

把获准的迁移范围转为可核对的行为映射，实施目标结构并证明保留行为、说明有意差异。旧实现与旧测试是证据基线，不是不可更改的目标；目标由本次用户要求及已确认契约决定。

## 1. 确定范围、规则与当前阶段

- 查看工作区状态，读取目标仓库适用的 AGENTS.md、实际脚本、测试配置、CI、设计记录和受影响实现；提交、代码风格、覆盖率及完整门禁沿用项目规则。
- 确认本次迁移对象、目标结构、需保留行为、允许变化、消费者及数据边界。只处理已授权范围，不把单独补测试或局部修复扩大为迁移。
- 定位现有工作的阶段：范围与基线、审计与裁决、实施、验证、验收。已有证据和有效决定直接复用；中途接入只补足当前范围内缺失的必要证据，不重启整仓流程。
- 代码与文档冲突先核实差异；若影响目标契约、权限或不可逆结果且证据不足，再询问用户。普通结构选择自主决定，用户未回复不能视为授权。
- 推送、发布、部署、工单回写、真实凭证及付费检查按本次授权处理；迁移技能本身不授予这些权限，也不强制创建提交或 PR。

## 2. 建立基线与迁移记录

按项目既有位置与格式记录目标、实施顺序和迁移证据，规模小时合为一份，不机械创建三份文档。内容要覆盖：

1. 当前可观察行为、目标行为及有意差异的依据。
2. 受影响模块、消费者、契约、持久化状态、生命周期与依赖方向。
3. 审计与迁移矩阵、测试计划、阶段验收、回退及旧接口清理条件。

大型迁移可将内容分为设计基线、实施计划与单元迁移记录，详见 [迁移文档](references/documents.md)。先基于证据起草，再确认存在实质分叉的决定；文档状态由证据推进，不能用“已定稿”替代验证。

## 3. 审计与裁决

对迁移范围内的旧实现、实际调用方及测试做盘点，追踪跨边界依赖，不默认审计整个仓库。按 [审计细则](references/audit.md) 检查正确性、契约、状态与依赖，区分实测、代码推断和未知。

每项行为标明保留、修正或移除；每个实现项可选择复制、局部修正、重构、重写或不迁移，并附证据与后果。旧测试逐项记录保留、改写或删除的理由，不能静默丢失覆盖，也不能复制只复述实现的无效断言。

已证实旧缺陷按任务授权决定修复与回归；超出范围的问题报告影响及归属，不因“旧行为”将其固化为新目标，也不擅自扩展修复。

## 4. 划分可验证单元

- 以可观察业务路径划分迁移单元，列对应旧行为、目标位置、消费者、测试入口和完成证据。
- 区分机械迁移与行为优化；风险高时先保持已确认行为的可追踪映射，再独立实施获准的语义变化。结构可重组，不要求新旧文件镜像，也不能把结构同构当作行为等价的证明。
- 先迁一个真实垂直单元，验证调用、装配、数据与测试路径，再推广相同方法。已在进行的迁移可用下一个待迁单元校准流程。
- 接口变更须迁移受影响调用方、测试和文档，核对消费者后再删旧接口。持久化或外部契约须先落实获准的数据转换、消费者切换及回退条件；必要过渡有明确退出条件，不能盲删也不永久保留双轨。

## 5. 逐单元实施与验证

1. 先取得当前基线和目标验收用例，确保期望来自独立规则或已确认行为。bug 修复先验证症状用例失败，再确认修复通过；无法取得修复前证据时如实记录。
2. 逐片实施，先运行受影响检查，再按目标项目要求执行阶段与交付的完整门禁。测试、覆盖率和命令从实际配置取得，不自行添加固定指标或平行验证体系。
3. 保留行为通过相同的可观察契约验证；有意差异逐项关联需求决定和测试，装置变动单独登记，避免以改断言迁就实现。
4. 失败按迁移偏差、原有缺陷、装置问题或环境阻塞归因，记录证据与责任范围。项目要求的门禁仍失败时不能宣称阶段完成，不能通过缩窄范围、跳过用例或降低阈值放行。
5. 跨边界行为复用既有集成、浏览器和进程验证入口；只有确有缺口时补最小装置。详见 [验证装置](references/e2e-harness.md)，故障定位见 [缺陷定位](references/debugging.md)。

## 6. 独立审查

风险集中于契约、权限、并发、资源或数据迁移时，审查目标记录与实现；机械批次可合并检查，但每项重要行为变化须有证据覆盖。独立审查须能读取旧实现、目标差异和测试迁移矩阵，详见 [审查细则](references/adversarial-review.md)。

协作使用当前宿主实际可用的委派工具，默认继承模型，审查者只读。能力缺失时报告限制，不能把自查称作独立审查；项目明确要求独立审查时，缺失的检查仍须列为未完成。需要明确的多轮 PR 审查且 `pr-review-loop` 可用时再采用，普通审查按本文执行。

## 7. 验收

- 所有保留、修正与移除的行为均有记录、依据和验证结果；消费者、持久化及旧接口清理条件逐项核对。
- 项目要求的完整门禁通过，重要审查发现有修复或证据充分的处置结论；未完成或失败项不能被写成通过。
- 真实环境检查仅在相关且获准时执行。缺少凭证、预算或权限时报告限制；若它是本次明确要求的验收项，保持该项未完成，不能以替身结果冒充。
- 按实际结果报告测试数、适用覆盖率、行为差异、遗留风险和阻塞归属，清理本次临时资源，并同步项目要求的文档。
- 提交与回退遵循项目约定及已有授权；保存进度不意味着可以自行推送、部署或修改共享环境。

## 可选协作

本技能自足，缺少其他技能时按本文继续，不先安装依赖或创建额外工作流。

- 普通新能力由 `feature-dev` 组织；只有其中明确的架构迁移部分使用本流程。
- `to-spec` 仅在需整理目标规格时参考；已有需求不重复采访或发布。
- `tdd` 仅用于 bug 回归或用户明确要求 test-first 的切片。
- `verify-harness` 仅用于系统性验证或确有装置缺口；缺少它时按本文的验证装置细则补足当前缺口。
